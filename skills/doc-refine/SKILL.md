# Technical Documentation Design & Refinement (`doc-refine`)

このスキルは、固定の見出しテンプレートで文書を画一化するのではなく、対象文書の目的・想定読者・書き手の動機（種：Seed）を活かしながら、読者がつまずきやすい **3つの摩擦** を解消するための段階的ドキュメント設計プロトコルです。

1. **知覚と初動の摩擦**: 開いた最初の数秒で「何をするものか」「なぜ・いつ使うのか」が分からず閉じられてしまう摩擦。
2. **認知と呼吸の摩擦**: 空間的な過密・平坦な箇条書き・息切れする長文や単調な構文によって処理負荷が膨らむか、逆に要約・短文化で必要な仕様や機能語が削られて理解できなくなる摩擦。
3. **論理と信頼・境界の摩擦**: 無根拠な誇張や装飾、「〜すべき」という説教調、言いっぱなしの制限事項、曖昧な値域制約や動的入出力例の欠如によって警戒や誤用を招く摩擦。

**基本姿勢**: 最初から1回の出力で「構造・論理・仕様境界・文体リズム」を同時に完成させようとすると、流暢な言い回しで論理の穴や事実の抜けが覆い隠され、ルール一括適用による見落としも増えます。そのため、**「事実収集 → 形容を削ぎ落とした裸の最小構成で骨格合意 → 自然言語化 → 次元別の独立監査」** の4段階で組み立てます。

---

## 実行モードのスケーリング（Full / Lite）

対象文書の規模と変更範囲に応じて、2つのモードを使い分けます。

| モード | 適用対象の例 | 実行の粒度 |
| :--- | :--- | :--- |
| **Full** | README の新規作成・全面改稿、設計書・仕様書・RFC、技術解説記事全体 | Stage 1〜4 をフル実行。Stage 1（事実調査）と Stage 4（Part I / Part II の2系統監査）は、利用可能であれば独立コンテキスト（サブエージェント等）へ委譲する。 |
| **Lite** | 既存文書の1セクション追記、PR説明、短い `.txt` メモ、コード内コメント | Stage 1 のファクト抽出と Stage 2 の裸の最小構成を数行に簡略化し、Stage 4 は同一コンテキスト内で「Part I のみ → Part II のみ」の2パス順次点検として軽量に回す。 |

---

## 実行ワークフロー（4-Stage Pipeline）

### Stage 1: 事実・実装・周辺制約の収集（ファクトリスト化）

細部のコード照合で認知予算を使い切って構造の問い直しが抜ける現象（アンカリング）を防ぐため、最初に機械的・事実的な確認を切り出します。

- 対象リポジトリの実装・設定・テスト（`package.json`, `Cargo.toml`, `pyproject.toml`, CLIパーサー定義、テストスイート等）から、以下の **ファクトリスト** を収集します：
  - 記載コマンド・引数・設定キー・パスと実装の一致／矛盾、再現コマンドの有無
  - パラメータの具体的な型・値域・デフォルト値・境界値・エラー挙動、および確認できる具体的な入出力例
  - ビルド／監査／配布スクリプト等が見出し階層やファイル構成に課す周辺制約
  - 既存文書内の規範表現（`〜すべき` / `should` 等）や無根拠な誇張の候補
- **実行方式**: Full かつ独立コンテキスト（サブエージェント等）が利用できる環境では、この調査を独立した調査エージェントへ委譲します。非対応環境または Lite では、まずファクトリストだけを簡潔に抜き出してから Stage 2 へ切り替えます。

### Stage 2: 文脈・種判定と「裸の最小構成ブループリント」＋ 合意（Hard Stop）

いきなり流暢な文章を書き始める前に、[references/context-adaptation.md](references/context-adaptation.md) と [references/logic-and-credibility.md](references/logic-and-credibility.md) を参照し、論理と情報の骨格を丸裸にします。

1. **文脈・読者層・種（Seed）の特定**:
   - 文書種別・媒体（GitHub README、内部設計書・RFC、APIガイド、技術解説記事、プレーンテキスト、コードコメント等）、想定読者の熟練度（専門外読者か保守担当者か）、および書き手固有の動機・ユーモア・語り口・外部記事導線といった **「種（Seed）」** を特定します。
   - 重点を置く柱と、あえて控える要素（例：ジョークアプリに重厚な課題論証や3段制約表を持ち込まない、内部仕様書に不要な1行インストール手順を作らない等）を決めます。
2. **ゼロベース再構成チェック**:
   - 既存文書がある場合、守る対象は書き手の「種」と事実であり、**現在の見出し順や段落配置そのものは保護対象とみなしません**。「白紙から『種』とファクトリストだけで組み直すならどう並べるか」と対比し、配置負荷や情報欠落（Why / When、値域境界、動的I/O例、制約の理由・回避策など）を診断します。
3. **「裸の最小構成ブループリント」の作成**:
   - **あらゆる形容詞・装飾・丁寧な繋ぎ言葉を削ぎ落とした羅列** として、各層（第1層〜第3層）の配置、形式割り当て（箇条書き／文見出し＋図／表）、および載せる事実・命題・因果鎖・値域境界・動的I/O例・制約3点セットを箇条書きで組み立てます。
   - 例（イメージ）:
     ```text
     [第1層：冒頭]（形式：定義2文＋単一手順＋最小コード）
     - 対象: <環境>製<分類> / 入力:<A> -> 出力:<B> / 外部依存:<数>
     - Why/When: <既存手段の不便> -> <適する場面>
     [第2層：設計と境界]（形式：文見出し＋散文＋境界表）
     - 因果: <仕組み> -> <動作機序> -> <読者の変化>
     - 値域/I/O: <範囲・異常時挙動> / 入力<X> -> 出力<Y>
     - 制約3点セット: [事実] / [トレードオフ理由] / [回避・代替]
     [第3層：詳細]（形式：<details>折りたたみ または Appendix）
     - 全オプション表・再現テストコマンド
     ```
4. **ユーザーへの提示と停止ルール（Hard Stop）**:
   - 以下4点を簡潔に提示します：
     1. **読み取った文脈・想定読者・活かす「種」**（および Full / Lite 判定）
     2. **裸の最小構成ブループリント**（既存構成から大きく組み替える理由や周辺スクリプト追従範囲を含む）
     3. **あえて控える要素と確認事項**（絵文字を含めない方針の要否、見出しが多い場合の目次要否など）
     4. **不足情報の確認質問**（必要な場合のみ1〜3個：作ったきっかけ、比較ベースライン、トレードオフ理由等）
   - 実行環境に質問ツールがある場合はそれを使用し、ない場合はチャットテキストで提示して **即座にターンを終了（Hard Stop）** し、ユーザーの承認を待ちます。
   - ※例外：ユーザーから「質問なしで最後まで一気に出力して」「バッチ処理で進めて」等の明示指示がある場合に限り、Hard Stop をスキップして Stage 3 へ進みます。

### Stage 3: 自然言語化と形式実装（ドラフト執筆）

ユーザーの承認と回答を受けたら、確定した最小構成ブループリントとファクトリストを土台に、[references/structure-and-rhythm.md](references/structure-and-rhythm.md) と [references/context-adaptation.md](references/context-adaptation.md) を参照してドキュメント本文を書き起こします。

- Stage 2 で確定した事実・論理・境界・有益な詳細を削らずに配置します（情報の非圧縮）。
- ここで初めて、書き手の「種（Seed）」の温度感を乗せ、構造化形式（箇条書き・文見出し・表・説明的図解）の使い分け、コードと出力・解説の空間的近接、黙読の一呼吸と文長の緩急を整えます。

### Stage 4: 次元別の独立監査・競合統合・仕上げ

執筆直後の同一コンテキストには確証バイアスが働きやすく、全ルールを一括チェックすると見落としが増えます。そのため、観点を **Part I** と **Part II** の2系統に分離して監査します。

1. **2系統の次元別監査**:
   - **監査パスA（Part I：知覚・空間構造・リズム）**:
     - [references/structure-and-rhythm.md](references/structure-and-rhythm.md) **のみ** を参照し、対象ドラフトと文脈・種メモに対して点検します。
     - 観点：初動1画面・Why/When・偽の床／3〜5チャンク・空間近接・段階的開示・形式選択（箇条書き平坦化／文見出し／表／図解）／黙読の一呼吸・係り受けと短文化の罠（語彙密度過多）・並列構文と散文ゆらぎ・5種のスタイル欠陥・問いかけ頻度・装飾記号の負荷。
   - **監査パスB（Part II：論理・誠実さ・境界・実装整合）**:
     - [references/logic-and-credibility.md](references/logic-and-credibility.md) **のみ** と Stage 1 のファクトリストを参照し、対象ドラフトに対して点検します。
     - 観点：既知から未知への因果鎖・迂回除去・未定義語彙・構造的一致／背理法・対偶とトレードオフの峻別／規範語（`〜すべき` / `should`）の排除／無根拠な誇張・比較基準・フォーマット装飾バイアス／反論あり両面提示／曖昧制約（`invalid` 等）の排除と具体的な値域境界・動的I/O具体例／ファクトリストとの実装整合・追試コマンド／スキル内部用語や論文名の露出有無。
   - **実行方式（ツール非依存）**:
     - **Full かつ独立コンテキスト（サブエージェント等）が利用できる環境**: 監査パスAと監査パスBをそれぞれ別の独立コンテキストへ委譲し（可能なら並列実行）、「問題箇所・理由・修正案」の指摘リストを受け取ります。
     - **非対応環境または Lite**: メインエージェントがまず「パスAのみ」の観点でドラフトを監査し、次に「パスBのみ」の観点へ明示的に切り替えて順次点検します。
2. **任意の絵文字制御（該当時のみ）**:
   - Stage 2 で「絵文字を含めない方針」に合意した場合、またはユーザーから混入検査を求められた場合に限り、[references/emoji-control.md](references/emoji-control.md) を参照して抑制・スクリプト検証・目視確認を行います。
3. **競合統合ルールと最終仕上げ**:
   - パスA（読みやすさ・リズム）とパスB（論理・境界・厳密さ）の指摘が競合した場合は、以下の優先順位でメインエージェントが統合・修正します：
     1. **事実・実装整合・境界条件は削らない**: 厳密さを増す追記で文が重くなる場合は、情報を削除せず「文の分割・表化・第3層への段階的開示」で呼吸と構造を回復する。
     2. **「種（Seed）」と文脈を保護する**: 書き手のユーモア・語り口・対象ジャンルを壊す画一的な修正指摘は採用しない。
     3. **自然な語り口を保つ**: スキル内部の用語（「裸の最小構成」「反論あり両面提示」「ヒュームのギロチン」「Level A構文」「5大スメル」等）や論文名を出力ドキュメントの地の文へ露出させない。
4. **最終出力と監査サマリー**:
   - 最終版ドキュメントを出力（またはファイル更新）したうえで、**「監査で反映した主な改善点」と「種や文脈を優先してあえて見送った指摘（トレードオフ）」を3〜5行の短いサマリー**として添えます。
