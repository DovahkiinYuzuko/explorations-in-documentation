# doc-refine Layer 3 詳細監査基準リファレンス
## 信頼性・両面提示・誇張排除・論証モデルの定量的評価仕様

本リファレンスは、`doc-refine` スキルにおいてドキュメントの信頼性シグナリング、制約事項開示、誇張表現排除、および論証構造（Layer 3: Credibility & Two-Sided Signaling）を客観的・論理的に監査・リライトするための詳細判定基準である。

---

## 1. Layer 3 監査判定基準マトリクス

| 監査項目 | 判定ルール | 違反時の判定 |
| :--- | :--- | :---: |
| **① 必須制約セクション** | `## Limitations & Boundaries` または `## Non-Goals` 等の専用見出しが存在するか。<br>※「利用上の注意」や「Caveats」等に実質的制約が記載されている場合は、FAILではなく見出し正規化の **WARN** とする。 | **完全欠落: L3 FAIL**<br>非標準見出し: L3 WARN |
| **② 反論あり両面提示構文** | 開示された制約が単なる箇条書き（反論なし）になっておらず、**「制約事実 ＋ 設計理由 ＋ 代替策/解消ロジック」** の3連構造を満たしているか。 | **単なる列挙: L3 WARN** |
| **③ 開示制約の重要度** | 開示された制約がツールのコア存在意義を自己否定（致命的欠陥）しておらず、かつ自明な些細事項でもない**「中程度の重要度（対象規模・前提環境の境界）」** に収まっているか。 | **コア品質否定: L3 FAIL**<br>些細すぎる開示: L3 WARN |
| **④ 誇張表現・BAKAワード** | 客観的ベンチマーク条件や機械的検証可能性を伴わない主観的誇張形容詞（"ultimate", "blazing fast"等）が使われていないか。 | **検出時: L3 FAIL** |
| **⑤ 論証結合構造（Toulmin型）** | 性能や品質の主張（Claim）に対し、Data（実測値）、Warrant（理由）、Backing（裏付け）、Rebuttal（例外）が結合しているか。 | **根拠なき主張: L3 FAIL**<br>Rebuttal欠落: L3 WARN |
| **⑥ 深層の透明性と自律性** | 自動化挙動やテレメトリに対し、内部動作の開示と完全なオプトアウト／カスタマイズ手順（Autonomy）が提示されているか。 | **オプトアウト不可: L3 WARN** |

## 2. 反論あり両面提示（Refutational Two-sided）の構文仕様

単に弱点を列挙しただけの記述は読者の離脱を招く。制約事項を開示する際は、必ず「なぜその設計なのかという理由」と「どう回避できるかという代替策」をセットで提示する。

### 2.1 必須記述テンプレート（3連構文）
制約セクション（`## Limitations & Boundaries` 等）内の各項目は、必ず以下の3要素を対にして記述する：

```markdown
- **[制約事項・非推奨ユースケース]**: [本ツールが対応していない領域、または性能劣化が生じる境界条件]
  - *設計理由（トレードオフ）*: [なぜその制約が存在するのか。何を優先した結果としてのトレードオフか]
  - *代替策・推奨構成*: [読者がその状況に直面した場合のワークアラウンド、設定変更、または推奨される代替ツールの提示]
```

#### 具体例 (Good vs Bad)
- ❌ **Bad (反論なし両面提示 / L3 WARN)**:
  ```markdown
  ## Limitations
  - 大規模分散クラスタ環境では動作しません。
  - メモリを大量に消費することがあります。
  ```
- ⭕ **Good (反論あり両面提示 / L3 PASS)**:
  ```markdown
  ## Limitations & Boundaries
  - **単一ノード実行特化（分散クラスタ非対応）**:
    - *設計理由*: ネットワークオーバヘッドを排除し、単一マシン上でのローカルディスクI/Oスループットを最大化するための意図的な設計決定です。
    - *推奨構成*: 複数マシンに跨るTB級ログ集計を行う場合はApache Sparkの利用を推奨します。単一マシンで完結する100GB未満のログ解析に特化して最大の効果を発揮します。
  - **インメモリ全量展開によるRAM消費**:
    - *設計理由*: ゼロコピーシリアライズによる検索速度最大化のため、インデックスを全量RAM上に保持します。
    - *代替策*: 利用可能RAMがデータサイズの1.5倍未満の場合は、起動オプションに `--mmap` フラグを付与することでディスクマッピングモードへ切り替え可能です。
  ```

## 3. 開示制約の重要度設計（中程度の重要度原則）

開示する制約の重みを以下の3水準に分類して監査する：

```
[致命的欠陥 (Core Failure)] ──> 開示ではなくコード/設計修正が必要 (L3 FAIL)
[中程度の重要度 (Moderate)]  ──> 信頼性・採択意向を最大化する最適開示領域 (L3 PASS)
[些細な事項 (Trivial)]      ──> 信頼シグナルとして機能せずノイズとなる (L3 WARN)
```

1. **致命的欠陥（Core Failure - 開示不可）**:
   - 例: 「稀に保存したファイルが破損します」「暗号化キーがハードコードされています」。
   - ドキュメントで開示しても信頼は得られず、採択意向を破壊する。即座に設計バグ修正を要する。
2. **中程度の重要度（Moderate Importance - 推奨開示）**:
   - 例: 対象規模の境界（「10万レコード以上は非推奨」）、特定のOS/言語ランタイム要件、同期型APIであること。
   - コア価値を担保しつつ、適合領域の境界線を明確にする。
3. **些細な事項（Trivial - 開示不適）**:
   - 例: 「ロゴの色が青系しかありません」「CLIヘルプのフォントは等幅です」。
   - 開示しても読者のリスク判断に寄与せず、無用な認知的負荷を増大させる。

## 4. 誇張表現・BAKAワード排除辞書 (Hype Purge Dictionary)

主観的形容詞や宣伝的な誇張表現は読者の不信を招く。
以下の単語がドキュメント内に検出され、客観的ベンチマークや検証コマンドが伴っていない場合は **L3 FAIL** を適用し、事実的記述へとリライトする。

### 4.1 検出対象単語とリライト規則

| 検出対象カテゴリ | 検出禁止語（BAKAワード） | リライト方針（客観的機能事実への変換） |
| :--- | :--- | :--- |
| **絶対的・最上級表現** | `ultimate`, `best-in-class`, `supreme`, `perfect`, `flawless`, `世界最高`, `究極`, `完全無欠` | 削除し、対応している仕様・標準規格の名称を具体的に記載する。 |
| **速度・性能の誇張** | `blazing fast`, `lightning fast`, `super fast`, `ultra lightweight`, `爆速`, `超高速`, `超軽量` | ベンチマーク数値（例: `実行時間 12ms (データサイズ 1MB)`）と計測環境へ置換する。 |
| **革命・過剰演出** | `revolutionary`, `game-changing`, `next-generation`, `magic`, `革命的`, `次世代`, `魔法のような` | アーキテクチャの具体的差分（例: `非同期イベントループの採用`）へ置換する。 |
| **無限・無制約の誇張** | `infinite`, `unlimited`, `zero-overhead`, `無制限`, `無限`, `オーバーヘッドゼロ` | 物理的制限値やリソース計算式（例: `RAM容量に依存 (要素あたり 32 bytes)`）を明記する。 |

## 5. 論証結合構文仕様 (Claim-Data-Warrant-Backing-Rebuttal)

性能やアーキテクチャの優位性を語るセクションでは、以下の5要素が揃っているかを監査する：

```markdown
1. **Claim (主張)**: 「本ライブラリは、大量アクセス環境において応答遅延を安定させます。」
2. **Data (事実・実測値)**: 「10,000 req/secの負荷テストにおいて、99パーセンタイル遅延は 4.2ms を記録しました。」
3. **Warrant (推論理由)**: 「スレッドプール枯渇を防ぐ非同期I/Oと、メモリ再割り当てを抑えるオブジェクトプーリングを採用しているためです。」
4. **Backing (裏付け)**: 「Go 1.22の公式netpollランタイム上で計測（テストコード: `test/bench_test.go`、CPU: AMD EPYC 7763 64-Core、RAM: 256GB）。」
5. **Rebuttal (例外・無効化条件)**: 「ただし、1リクエストあたりのペイロードが 50MB を超える場合、GCの一時停止によりレイテンシが最大 85ms まで悪化する例外条件が存在します。」
```

### 5.1 運用基準
- **コア主張への集中**: 論証結合構造は、ツールの存在意義に関わる「中核の性能主張・セキュリティ主張（1〜2箇所）」に限定して適用する。
- **段階的開示の併用**: 詳細なBacking（ベンチマークスクリプト、再現手順、詳細ハードウェア構成）や数式が20行を超える場合は、`<details>` により折りたたんで配置する。

## 6. システム透明性と自律性保障 (Transparency & Autonomy)

1. **内部挙動の透明性**:
   - 外部通信、テレメトリ送信、キャッシュ生成、ファイル書き込みを行うツールである場合、その通信先・保存場所・収集内容が明記されているか。
2. **オプトアウト・制御可能性**:
   - テレメトリや自動バックアップ等の機能に対し、環境変数（例: `DO_NOT_TRACK=1`）や設定フラグ（例: `--no-telemetry`）による完全な遮断・無効化手順が記載されているか。
3. **再現可能な検証コマンド**:
   - ドキュメント内の主張が、読者の手元で即座に検証できるコマンド（テスト実行、ヘルスチェックコマンド）に接続されているか。
