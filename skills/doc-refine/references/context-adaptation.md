## 1. なぜ文脈適応と読者層の見極めが必要なのか

どれほど優れた設計原則であっても、すべての文書に同じ見出し構成・同じ情報密度・同じ形式を機械的に当てはめると逆効果になります。
- **読者層の熟練度による反転**: 専門外の初見読者には専門用語を抑えた導入と最小実行例が役立ちますが、すでにドメイン知識を共有している同僚や保守担当者向けの内部仕様書に初歩的な導入を書くと、かえって読解の邪魔になります（専門性の逆転）。逆に、保守引き継ぎ文書で細粒度の境界条件や内部構造を省くと実用になりません。
- **手慣れた形式と目的のトレードオフ**: 操作手順書のようにシナリオが明確な文書は手順の一貫性が重視される一方、概念や設計思想を伝える文書では前提から結論への論理と図解が鍵になります。また、読者や書き手は慣れ親しんだ「箇条書きだらけの形式」を主観的に好む傾向があるため、文見出しや表へ切り替える際は対象文書の目的と読者層に照らして自然なバランスを選びます。
- **書き手の「種（Seed）」と自律性の保護**: ジョークアプリや個人制作物に重厚な課題論証や3段構えの免責リストを押し付けると本来の魅力が消えて野暮になります。また、マークアップが使えないプレーンテキスト（`.txt`）に GitHub 専用記法を持ち込むと崩れます。

そのため、Stage 2 で「誰が何のために読むのか」「書き手が伝えたい核（種）は何か」を見極めたうえで、5つの柱の重み付けと適用範囲を調整します。

## 2. 文書種別・プロジェクト性質ごとの重み付けガイド

### 2.1 実用CLIツール・OSSライブラリ・SDK
- **読者の関心**: 「自分の課題を解決できるか」「今すぐ手元で動かせるか」「本番や自分の環境に入れて安全か（境界や罠はないか）」。
- **重点を置く原則**:
  - **初動と最短動線**: 最初の画面での具体的入出力定義・Why / When、単一の標準インストール手順と基本構文による最小実行例。
  - **空間構造と形式選択**: ハッピーパス（第1層）と詳細リファレンス（第3層）の段階的開示、オプション・フラグ一覧の表構造化（並列構文で走査速度を上げる）。
  - **境界開示と検証可能性**: 比較基準付きデータ、反論あり両面提示（制約事実＋理由＋回避策）、具体的な値域制約と動的I/O具体例、手元で追試できるテストコマンド。
- **あえて控える要素**: 説明文中の頻繁な問いかけ、意味的距離の遠い装飾記号の乱用。

### 2.2 エンタメ・ジョークアプリ・個人Webトイ
- **読者の関心**: 「何これ面白い」「どうやって遊ぶの」「なぜこれを作ったの」。
- **重点を置く原則**:
  - **入口の動機づけと「種」の保護**: ユーモアや温度感を保ったまま一目で何のおもちゃか伝わる冒頭文、デモ画面（スクリーンショットやGIF）、公開URLや制作背景記事への分かりやすい導線。
  - **手軽な体験手順と軽快な呼吸**: ブラウザで開くだけ、あるいは数コマンドで試せる手順と、テンポよく読める文体。
- **あえて控える要素（野暮の回避）**:
  - 堅苦しい学術的・工学的な課題定義の長文。
  - 大袈裟なパフォーマンス比較表や重々しい3段構成の免責・制約セクション（動作環境や軽い注意書きで足りるなら自然な1〜2文に留める）。
  - 短い文書に無理やり `<details>` 折りたたみ・目次・過剰な値域仕様表を入れてクリックの手間を増やすこと。

### 2.3 内部アーキテクチャ設計書・仕様書・RFC
- **読者の関心**: 「なぜ代替案ではなくこの設計を選んだのか」「モジュール間の境界とデータフローはどうなっているか」「エッジケースや異常時にどう振る舞うか」。
- **重点を置く原則**:
  - **論理と構造的一致**: 前提課題からの演繹的連鎖、背理法（必須要件との矛盾）とトレードオフ比較の峻別、実際のディレクトリ・モジュール構造と対応した見出し構成、説明的ダイアグラム。
  - **厳密な境界と契約**: `should` や `invalid` を避けた検証可能な仕様事実・条件付き因果、値域制約・状態遷移表・動的I/O具体例（境界値・エラー系含む）。
  - **散文の呼吸とスメル除去**: 絡み合い（Tangled）や断片化（Fragmented）を避け、設計判断の散文では構文の単調さを防ぐ。
- **あえて控える要素**: パッケージ公開用バッジや、対象に存在しない「1行インストール（Quick Start）」の押し付け。

### 2.4 技術解説記事・Zenn / note / ブログ・論考
- **読者の関心**: 「どんな問いやきっかけから始まったのか」「どういう仕組み・理屈なのか」「自分の開発や思考にどう活かせるか」。
- **重点を置く原則**:
  - **共感を生む入口（種）と文見出し**: 書き手の素直な疑問や動機から入り、見出しと目次で全体の見通しを作る。論点を伝える節では主張の分かる文見出しと図解を活用する。
  - **時間的リズムと既知から未知への語り口**: 一呼吸で追いやすい係り受け・句読点、長文と短文の緩急、構文のゆらぎ。節の切り替えに要点直結の問いかけを1つ置くのは有効だが、本文中で高頻度に乱発しない。
  - **非説教トーン**: 「〜すべき」で読者にマウントを取らず、事実・条件付き因果・知見共有のスタンスを保つ。

### 2.5 プレーンテキスト（`.txt`）・コード内コメント・PR説明
- **読者の関心**: マークアップのない環境やコードレビュー中に、素早く要点・変更理由・境界条件を把握すること。
- **重点を置く原則**:
  - **記法非依存の段階的開示とチャンク化**: `<details>` が使えない環境では冒頭に結論・要約と主要手順を置き、詳細は末尾の `=== Appendix ===` または別ファイルへ分離する。空行とインデントで3〜5項目の塊を作る。
  - **非トートロジーと動的例**: コードコメントでは字面の言い換えを避け、背景（Why）・不変条件・境界挙動を書く。PR説明では変更前後の具体的な入出力・再現確認コマンドを添える。

## 3. 原則適用の Before / After 具体例

### 3.1 冒頭の定義と Why / When（宣伝文句から具体的事実へ）
- **Before（抽象的な宣伝文句と誇張）**:
  > **SuperParser**
  > 次世代の圧倒的に高速でスマートな究極の設定ファイルパーサーです。直感的なAPIで開発体験を劇的に改善します。
- **After（具体的な入出力定義・Why / When の明示）**:
  > **SuperParser**
  > コメントや末尾カンマを含む JSON（JSONC）を、外部依存ゼロで標準の JavaScript オブジェクトへ変換する TypeScript 製パーサーです。
  > 標準の `JSON.parse()` ではエラーになる設定ファイル（`tsconfig.json` や VS Code 設定ファイルなど）を、コメントの位置情報を保持したまま読み書きしたい場面に適しています。

### 3.2 規範文（ought）から仕様事実・条件付き因果（is / If-Then）へ
- **Before（説教調・規範の押し付け）**:
  > 大規模なファイルを処理する際は、メモリ不足を防ぐために必ず `--stream` オプションを使用しなければなりません。一括読み込みは使うべきではありません。
- **After（仕様事実と条件付き因果）**:
  > デフォルトのモードではファイル全体をメモリ上に展開して解析するため、入力ファイルサイズの約3倍のヒープメモリを使用します。数百MBを超えるログファイルなど、メモリ使用量を一定（約16MB）に抑えたい環境では、`--stream` オプションを指定すると行単位の逐次処理に切り替わります。

### 3.3 裸の制限事項から反論あり両面提示へ
- **Before（弱点の裸の放置：不採用理由になる）**:
  > **制限事項**
  > - マルチスレッド並列処理には対応していません。
  > - プラグインによる動的構文拡張はできません。
- **After（事実＋設計上のトレードオフ理由＋対処法）**:
  > **設計上のスコープと制約**
  > - **シングルスレッド実行**: 実行順序の決定論的な再現性とデバッグの容易さを優先し、内部でのマルチスレッド並列化は行っていません。数千ファイル規模のバッチ処理を並列化したい場合は、OS側の `xargs -P` や GNU Parallel から複数プロセスとして呼び出す構成が適しています。
  > - **固定構文仕様**: 起動速度とバンドルサイズ（gzip後 4KB）を小さく保つため、実行時の動的プラグイン機構は備えていません。独自構文の拡張が必要なケースでは、AST変換プラグインに対応するツールX等を検討できます。

### 3.4 エンタメ・ジョークアプリにおける温度感（種）の保護
- **Before（テンプレートの機械的押し付けによる「脱色」の失敗例）**:
  > ## Why（なぜこれが必要なのか）
  > 現代の画像処理パイプラインにおいて、非可逆圧縮アルゴリズムの視覚的劣化プロセスを体験的に理解することは重要です。既存の画像編集ツールは高画質化を目的としており、意図的な劣化を生成するには複数回の手動保存が必要であり非効率でした。本ツールはこの課題を解決します。
- **After（書き手のユーモアと「種」を活かしつつ、何ができるかを明確にした例）**:
  > **JPEGガビガビメーカー**
  > 画像を何度も再圧縮して、ネットの海で擦り切れたような「絶妙なガビガビ感（モスキートノイズ・ブロックノイズ）」をブラウザ上で好きなだけ作り出せるWebトイです。
  > 画質パラメータや縮小・引き伸ばし回数をスライダーでいじりながら、リアルタイムに画像が風化していく様子を楽しめます。詳しい制作のきっかけや仕組みは [こちらの記事（リンク）] にまとめています。

### 3.5 未定義の内部識別子・同義カッコ書きから読者目線の記述へ
- **Before（読者の知らない内部キー名や、意味のない日英カッコ書きが混在）**:
  > 各項目に対して 5 択（未決定 (pending) / 確定 (approve) / 差し戻し (revise)）を設定でき、新しい論点の追加提案（`proposed_agendas`）も行えます。ヘッダーから表示モード（`auto` / `desktop` / `mobile`）を切り替えられます。
- **After（実際の画面表記に揃え、内部キー名は開発者向けリファレンス層へ分離）**:
  > 各項目に対して「未決定 / 確定 / 差し戻し」のステータスを設定でき、同じ画面から新しい論点の追加提案も行えます。ヘッダーから表示モード（自動 / PC表示 / モバイル表示）を切り替えられます。
  > （※出力ファイルのキー名 `proposed_agendas` や内部定数 `pending` 等の仕様は、詳細リファレンスや折りたたみセクションに整理）

### 3.6 仕様の羅列から「仕組み → 動作機序 → 変化」の因果接続へ
- **Before（内部処理の事実だけを並べた箇条書き）**:
  > - **`.gitignore` 自動生成**: 初回実行時に出力先フォルダへ `*` と `!.gitignore` のみを記載した `.gitignore` を生成します。
- **After（仕組みが読者の作業にどう作用するかをつないだ記述）**:
  > - **リポジトリを汚さない出力**: 初回実行時に出力先フォルダへ `.gitignore` を自動生成するため、一時的な作業ファイルが Git の変更履歴に混ざりません。

### 3.7 平坦な箇条書き・単調な構文から、形式の使い分けと呼吸の通る文体へ
- **Before（因果関係がある説明を句見出し＋箇条書きへ平坦化し、同じ文末を連続させた例）**:
  > ### キャッシュについて
  > - キャッシュはメモリ上に保持されます。
  > - キャッシュの有効期限は60秒です。
  > - キャッシュはプロセス再起動で消えます。
  > - キャッシュを有効にするとAPI呼び出しが減ります。
- **After（結論の分かる見出しと因果のつながる散文＋仕様の分離）**:
  > ### インメモリキャッシュでAPI呼び出しを抑え、再起動時は自動で再取得する
  > 取得した設定値はプロセス内のメモリに60秒間保持され、そのあいだの重複したAPI呼び出しを省きます。永続化は行わないためプロセス再起動時にキャッシュは破棄され、初回アクセス時に最新値を自動で取り直します。

### 3.8 息切れ長文と極端な短文化（語彙密度過多）の調整
- **Before A（主語と述語が離れ、修飾が入れ子になって一呼吸で追えない長文）**:
  > このコマンドは、カレントディレクトリ配下に配置されている設定ファイルが存在する場合にのみその中身を読み込んで環境変数の値とマージしたうえで未定義のキーが含まれていないか検証してから対象スクリプトを実行します。
- **Before B（文字数だけ削って機能語を落とし、名詞が密集した難解な短文羅列）**:
  > 設定読込実施。環境変数マージ実行。未定義キー検証後、スクリプト起動。
- **After（論理をつなぐ機能語を保ちつつ、一呼吸の塊と緩急を整えた文）**:
  > カレントディレクトリに設定ファイルがある場合、まずその内容を環境変数とマージします。次に未定義キーの有無を検証し、問題がなければ対象スクリプトを実行します。

### 3.9 曖昧な制約表記から具体的な値域境界・動的I/O具体例へ
- **Before（`invalid` と `should` でぼかし、静的パラメータ名だけ並べた例）**:
  > `parsePort(input)` はポート番号を解析します。`invalid` な値を渡すとエラーになります。予約ポートは指定すべきではありません。
- **After（具体的な値域・境界挙動と動的I/O具体例を添えた例）**:
  > `parsePort(input)` は文字列または整数を TCP ポート番号（`1`〜`65535` の整数）へ変換します。`0` 以下・`65536` 以上・非整数を渡した場合は `RangeError` を送出します。なお、`1`〜`1023` は特権ポートとして扱われるため、OS の一般ユーザー権限でリッスンすると起動時に `EACCES` エラーが発生します。
  >
  > | 入力 `input` | 結果 / 挙動 |
  > | :--- | :--- |
  > | `"8080"` | `8080` を返す |
  > | `0` / `65536` / `"abc"` | `RangeError("Port must be an integer between 1 and 65535")` を送出 |
