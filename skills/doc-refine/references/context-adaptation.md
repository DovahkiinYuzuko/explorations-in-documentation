## 1. なぜ文脈適応が必要なのか（Why Context Matters）

どれほど優れた設計原則であっても、すべての文書に同じ見出し構成や同じ情報密度を機械的に当てはめると逆効果になります。
- すでにドメイン知識を共有している開発チーム向けの**内部仕様書**に、初歩的なインストール手順や「そもそも〇〇とは」という冗長な導入を書くと、熟達した読者の読解を妨げます（専門性の逆転効果）。
- 一瞬のユーモアや手軽さを楽しむ**ジョークアプリ**に、重厚なアーキテクチャ比較表や厳密なベンチマーク・3段構成の制約リストを並べると、作品本来の魅力（書き手の「種」）が消えて野暮になります。
- Markdownの折りたたみ（`<details>`）やバッジが使えない**プレーンテキスト（`.txt`）**に、GitHub README専用の記法を持ち込むと表示が崩れます。

そのため、執筆や推敲を始める前に「この文書は誰が何のために読むのか」「書き手が一番伝えたい核（種）は何か」を見極め、4つの柱の適用バランスを調整します。

## 2. 文書種別・プロジェクト性質ごとの重み付けガイド

### 2.1 実用CLIツール・OSSライブラリ・SDK
- **読者の関心**: 「自分の課題を解決できるか」「今すぐ手元で動かせるか」「本番や自分の環境に入れて安全か（罠はないか）」。
- **重点を置く原則**:
  - **最初の画面での具体定義**: 言語・動作環境・具体的な入出力の明示。
  - **最短動線の単一化**: 迷わない1つのインストールコマンドと、基本構文（Level A）のみで動く最小実行例。
  - **Why / When と比較基準**: 既存ツールや標準機能と比べてどの課題をどう解くのか、実測値がある場合は測定条件とベースラインの明示。
  - **段階的開示**: ハッピーパス（基本の3〜4機能）と網羅的リファレンス（全フラグ一覧・詳細な設定表）の階層分離。
  - **反論あり両面提示と再現手段**: 非推奨ケース・制限事項（事実＋設計上のトレードオフ理由＋回避策）と、テスト実行コマンドの提示。

### 2.2 エンタメ・ジョークアプリ・個人Webトイ
- **読者の関心**: 「何これ面白い！」「どうやって遊ぶの？」「なぜこんなものを作ったの？」。
- **重点を置く原則**:
  - **一目で伝わるコンセプトと視覚的導線**: 何をするアプリなのかがユーモアや温度感を保ったまま一瞬で伝わる冒頭文、デモ画面（スクリーンショットやGIF）、公開URLや制作背景記事（note / Zenn 等）への分かりやすいリンク。
  - **手軽に試せる手順**: ブラウザで開くだけ、あるいは数コマンドで動かせるシンプルな手順。
- **あえて控える要素（野暮の回避）**:
  - 堅苦しい学術的・工学的な課題定義の長文。
  - 大袈裟なパフォーマンス比較表や重々しい免責・制約セクション（ブラウザの動作環境や軽い注意書き程度で十分な場合は、自然な1〜2文に留める）。
  - 全体の分量が短い場合に、無理やり `<details>` 折りたたみや目次（TOC）を入れてクリックの手間を増やすこと。

### 2.3 内部アーキテクチャ設計書・仕様書・RFC
- **読者の関心**: 「なぜこの設計を選んだのか」「モジュール間の境界とデータフローはどうなっているか」「エッジケースや異常時にどう振る舞うか」。
- **重点を置く原則**:
  - **前提課題から設計選択への演繹的連鎖**: 要件・制約条件から出発し、なぜ代替案ではなくこの設計を採用したのかのトレードオフ比較（結果論証）または境界条件（背理法）。
  - **構造的一致とチャンク化**: 実際のディレクトリ・モジュール構造と対応した見出し構成、状態遷移やデータ構造のテーブル化。
  - **仕様事実と条件付き因果**: 「〜すべき」という曖昧な努力目標ではなく、「入力Xが条件Yを満たさない場合、関数ZはエラーEを返す」という検証可能な仕様記述。
- **あえて控える要素**:
  - パッケージ公開用のバッジ類や「1行インストール（Quick Start）」など、対象に存在しない要素の押し付け。

### 2.4 技術解説記事・Zenn / note / ブログ・論考
- **読者の関心**: 「どんな問いやきっかけから始まったのか」「どういう仕組み・理屈なのか」「自分の開発や思考にどう活かせるか」。
- **重点を置く原則**:
  - **共感を生む入口（種）と探索しやすい目次**: 書き手の素直な疑問や動機から入り、見出しと目次で全体の見通しを作る。
  - **既知から未知への自然な語り口**: 専門用語や概念を導入する際は、身近な具体例や既知の前提から順を追ってつなぐ。
  - **非説教トーン（ヒントと知見の共有）**: 「〜すべきだ」「〜しなければならない」と読者にマウントを取るのではなく、「こういう場面では〜という摩擦が起きやすい」「〜という仕組みを取り入れると解決しやすい」という知見共有のスタンスを保つ。

### 2.5 プレーンテキスト（`.txt`）・コード内コメント・PR説明
- **読者の関心**: マークアップのない環境やコードリーディング中に、素早く要点と意図を把握すること。
- **重点を置く原則**:
  - **記法に依存しない段階的開示**: `<details>` タグが使えない環境では、「冒頭に結論・要約（Summary）と主要手順を置き、詳細な仕様一覧や補足データは文書末尾の `=== Appendix ===` セクションまたは別ファイルへ分離する」ことで関心事の分離を実現する。
  - **インデントと空行によるチャンク化**: 1ブロック3〜5項目を目安に空行と記号（`-`, `*`, `[1]` 等）で視覚的な塊を作る。
  - **コードコメントにおける非トートロジー**: コードの処理内容をそのまま日本語でなぞるのではなく、「なぜその一見奇妙な処理が必要なのか（外部APIの仕様制限、パフォーマンス上の理由、エッジケース回避等）」という背景（Why）と不変条件（Invariant）を記述する。

## 3. 原則適用の Before / After 具体例

### 3.1 冒頭の定義と Why / When（宣伝文句から具体的事実へ）
- **Before（抽象的な宣伝文句と誇張）**:
  > ** SuperParser**
  > 次世代の圧倒的に高速でスマートな究極の設定ファイルパーサーです。直感的なAPIで開発体験を劇的に改善します。
- **After（具体的な入出力定義・Why/When・比較基準の明示）**:
  > **SuperParser**
  > コメントや末尾カンマを含む JSON（JSONC）を、外部依存ゼロで標準の JavaScript オブジェクトへ変換する TypeScript 製パーサーです。
  > 標準の `JSON.parse()` ではエラーになる設定ファイル（`tsconfig.json` や VS Code 設定ファイルなど）を、コメントの位置情報を保持したまま読み書きしたい場面に適しています。

### 3.2 規範文（ought）から仕様事実・条件付き因果（is / If-Then）へ
- **Before（ヒュームのギロチン・説教調）**:
  > 大規模なファイルを処理する際は、メモリ不足を防ぐために必ず `--stream` オプションを使用しなければなりません。一括読み込みは使うべきではありません。
- **After（仕様事実と条件付き因果）**:
  > デフォルトのモードではファイル全体をメモリ上に展開して解析するため、入力ファイルサイズの約3倍のヒープメモリを使用します。数百MBを超えるログファイルなど、メモリ使用量を一定（約16MB）に抑えたい環境では、`--stream` オプションを指定すると行単位の逐次処理に切り替わります。

### 3.3 裸の制限事項から反論あり両面提示へ
- **Before（弱点の裸の放置：不採用理由になる）**:
  > **制限事項**
  > - マルチスレッド並列処理には対応していません。
  > - プラグインによる動的構文拡張はできません。
- **After（事実＋設計上のトレードオフ理由＋対処法）**:
  > **設計上のスコープと制約**
  > - **シングルスレッド実行**: 実行順序の決定論的（Deterministic）な再現性とデバッグの容易さを優先し、内部でのマルチスレッド並列化は行っていません。数千ファイル規模のバッチ処理を並列化したい場合は、OS側の `xargs -P` や GNU Parallel から複数プロセスとして呼び出す構成が適しています。
  > - **固定構文仕様**: パーサーの起動速度とバンドルサイズ（gzip後 4KB）を小さく保つため、実行時の動的プラグイン機構は備えていません。独自構文の拡張が必要なケースでは、AST変換プラグインに対応するツールX等を検討してください。

### 3.4 エンタメ・ジョークアプリにおける温度感（種）の保護
- **Before（テンプレートの機械的押し付けによる「脱色」の失敗例）**:
  > ## Why（なぜこれが必要なのか）
  > 現代の画像処理パイプラインにおいて、非可逆圧縮アルゴリズムの視覚的劣化プロセスを体験的に理解することは重要です。既存の画像編集ツールは高画質化を目的としており、意図的な劣化を生成するには複数回の手動保存が必要であり非効率でした。本ツールはこの課題を解決します。
- **After（書き手のユーモアと「種」を活かしつつ、何ができるかを明確にした例）**:
  > **JPEGガビガビメーカー**
  > 画像を何度も再圧縮して、ネットの海で擦り切れたような「絶妙なガビガビ感（モスキートノイズ・ブロックノイズ）」をブラウザ上で好きなだけ作り出せるWebトイです。
  > 画質パラメータや縮小・引き伸ばし回数をスライダーでいじりながら、リアルタイムに画像が風化していく様子を楽しめます。詳しい制作のきっかけや仕組みは [こちらの記事（リンク）] にまとめています。
