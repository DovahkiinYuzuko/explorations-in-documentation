# doc-refine Layer 5 詳細監査基準リファレンス
## 実証根拠・検証可能性・決定論的再現性・数値因果検証の定量的評価仕様

本リファレンスは、`doc-refine` スキルにおいてドキュメントに記載された機能、性能、品質に関する主張（クレーム）が、読者の環境で機械的かつ客観的に追試・再現可能であるか（Layer 5: Empirical Evidence & Replicability）を監査・リライトするための詳細判定基準である。

---

## 1. Layer 5 監査判定基準マトリクス

| 監査項目 | 判定ルール | 違反時の判定 |
| :--- | :--- | :---: |
| **① 単体実行可能コマンド** | 機能の確認や動作検証を行うためのコマンドが、前提ツール・環境変数・引数を省略せずに単体で即座に実行可能な形式で提示されているか。<br>※「適宜設定して実行」などの曖昧な指示は違反。 | **検証手順欠落: L5 FAIL**<br>前提変数未定義: L5 WARN |
| **② 決定論的期待出力** | コマンドを実行した際に得られるべき「正常終了コード」「標準出力スニペット」「期待されるファイル状態」が具体的に明記されているか。<br>※「正しく動作します」などの主観的報告は違反。 | **出力期待値欠落: L5 WARN**<br>成否判定基準なし: L5 FAIL |
| **③ 数値クレームの因果文脈開示** | 「10倍高速」「90%削減」「軽量」などの定量的・比較的主張に対して、測定対象のベースライン、ハードウェアスペック、データセット規模、測定反復回数が開示されているか。 | **根拠なき数値誇張: L5 FAIL**<br>測定環境一部欠落: L5 WARN |
| **④ 環境依存性・動作境界の明示** | 動作確認が取れているOS、言語ランタイムバージョン、外部依存ライブラリのバージョン境界が明記されているか。 | **環境条件欠落: L5 WARN** |
| **⑤ 条件付き因果文への正規化** | 「〜を実行すべきである」という規範的表現を排し、「［前提環境］において［コマンド］を実行した場合、［結果］が得られる」という客観的事実命題として記述されているか。 | **規範的表現: L5 FAIL**<br>主観的誘導文: L5 WARN |

## 2. 単体実行可能コマンドと決定論的オラクルの仕様

### 2.1 自己完結コマンドの要件
読者がドキュメント内のコードブロックをターミナルに貼り付けた時点でエラーなく実行できる状態（Self-Contained）を担保する。

```markdown
<!-- Bad: 前提が不明で単体実行できない（L5 FAIL） -->
実行方法:
$ my-tool process

<!-- Good: 入力・オプション・出力先が完結している（L5 PASS） -->
```bash
# 入力サンプルファイルを生成して処理を実行
echo "sample-input-data" > input.txt
my-tool process --input input.txt --output result.json
cat result.json
```
```

### 2.2 決定論的期待出力（Expected Output）
コマンドの実行成否を機械的に照合できるよう、標準出力または生成成果物の具体例を直下に提示する。

```markdown
<!-- Bad: 成功時の挙動が読者の主観に委ねられている（L5 WARN） -->
実行すると正常に解析されます。

<!-- Good: 期待される終了コードおよび出力が明記されている（L5 PASS） -->
**期待される標準出力:**
```text
[SUCCESS] Processed 1 records in 12ms.
Output saved to: result.json (status: valid, checksum: a1b2c3d4)
```
```

## 3. 数値クレームの因果検証仕様

ハードウェア環境、データサイズ、ベースライン比較対象、測定誤差を伴わない単独の数値は、客観的検証に耐え得ない。

### 3.1 必須開示タプル（4-Item Benchmarking Tuple）
ドキュメント内で性能数値または効率性数値を提示する場合、以下の4要素を不可分に結合して開示する：

1. **測定環境（Hardware & Runtime）**: CPUモデル、RAM、OS、ランタイムバージョン（例: Apple M2 / 16GB RAM / Node.js v20.10.0）。
2. **測定対象データセット（Workload / Dataset）**: レコード件数、ファイルサイズ、入出力特性（例: 100,000行のJSONLinesデータ、総計42MB）。
3. **比較対照（Baseline）**: 比較対象となった既存ツール名およびバージョン（例: grep v3.11 との比較）。
4. **反復と統計量（Trials & Variance）**: 実行回数および代表値（例: 10回実行の平均値 $\pm$ 標準偏差、ウォームアップ3回除外）。

上記4要素が揃わない数値主張は、**「測定環境を付記した客観表」**へ変換するか、それが不可能な場合は**「事実としての機能記述」**へ降格する。

## 4. Good / Bad 対比カタログ

### ケースA: ベンチマーク・性能の主張
- **Bad (L5 FAIL / L3 FAIL)**:
  > 当ツールは圧倒的な処理速度を誇り、従来のパーサーと比較して10倍以上の高速化を実現しています。大規模データでも一瞬で終わります。
- **Good (L5 PASS / L3 PASS)**:
  > **ベンチマーク測定結果**
  > 以下の条件下において、100,000行（42MB）のJSONLパース処理時間を10回測定した中央値です。
  > 
  > | ツール | 平均処理時間 (秒) | メモリ最大消費 (MB) |
  > | :--- | :---: | :---: |
  > | 当ツール (v1.0.0) | 0.42 ± 0.03 | 18.4 |
  > | 従来実装 (v0.2.1) | 4.15 ± 0.21 | 84.2 |
  > 
  > *測定環境: AMD Ryzen 7 7800X3D, 32GB DDR5 RAM, Ubuntu 24.04 LTS (Node.js v22.2.0)*
  > *再現手順:*
  > ```bash
  > npm run benchmark -- --samples 10 --dataset fixtures/large-42mb.jsonl
  > ```

### ケースB: 動作確認・クイックスタート手順
- **Bad (L5 FAIL)**:
  > 設定ファイルを適切に配置した上で、サーバーを立ち上げてください。正しく設定されていれば動作するはずです。
- **Good (L5 PASS)**:
  > **動作確認手順**
  > 1. 最小構成ファイルを作成します:
  > ```bash
  > echo '{"port": 8080, "log_level": "info"}' > config.json
  > ```
  > 2. サービスを起動します:
  > ```bash
  > ./bin/server --config config.json
  > ```
  > 3. ヘルスチェックを実行して正常性を確認します:
  > ```bash
  > curl -s -f http://localhost:8080/health
  > # 期待される応答: {"status":"ok","uptime":1}
  > ```
