# 技術文書の4大設計原則（Principles of Technical Documentation）

本リファレンスは、新規起案・機能追記・構成整理・既存文面の推敲・仕様監査のいずれの場面でも一貫して機能する4つの設計原則を定義します。
固定の見出しテンプレートを押し付けるのではなく、各原則の「なぜそうするのか（解消する読者の摩擦と認知・論理メカニズム）」を踏まえ、対象文書の文脈に合わせて適用します。

## 1. 第1の柱：注意と導入（Attention & Onboarding）

### 1.1 最初の画面での具体定義と Why / When の提示
- **なぜそうするのか（Why）**:
  読者の視線と閲覧時間の大半は、スクロール前の最初の画面（First Viewport）に集中します。また視線は画面上部から左端に沿ってF字型に移動するため、冒頭に抽象的な宣伝文句（「次世代のソリューション」「スマートな体験」等）しか書かれていないと、読者は「自分の課題を解く文書かどうか」を判断できず即座に離脱します。さらに、機能一覧（What）と手順（How）だけでは、「なぜ既存のやり方ではなくこれを選ぶのか（Why）」「どういう状況・規模に向いているのか（When）」が伝わりません。
- **具体的な操作（How）**:
  - **字義通りの機能定義**: 最初の段落で、対象環境・カテゴリ・具体的な入出力（何を受け取って何を返すか）を具体的な名詞と動詞で記述します。
  - **Why / When の接続**: 「どのような具体的な不便・課題を解くために作られたか（Why）」と「どのようなユースケース・前提条件に適しているか（When）」を、冒頭の概要または導入セクションで明示します（独立した見出しにするか、概要の段落と統合するかは文書の規模とトーンに合わせます）。
  - **識別しやすい見出し**: 見出しや箇条書きの先頭（左端）に、具体的な機能語や行動動詞を配置します。

### 1.2 最短動線の単一化と基本構文（Minimal Onboarding）
- **なぜそうするのか（Why）**:
  利用者は長い前置きを読むよりも「まず手元で動かして確かめる」ことを優先します。しかし、導入部で複数のインストール経路（npm / pnpm / yarn / Docker / ソースビルド等）や設定オプションを並列に並べると、選択の迷い（決定麻痺）とタスク切り替えの負荷が発生します。また、最初のコード例に言語特有の高度なイディオム（複雑な内包表記、メタプログラミング、多重チェーン等）を含めると、初見読者の認知負荷が跳ね上がります。
- **具体的な操作（How）**:
  - **単一の最短経路**: 実用ツールやライブラリでは、標準的な1つの導入コマンドと、コピー＆ペーストでそのまま動く最小実行例（3〜10行程度）を提示します。代替のインストール手段やプラットフォーム別手順は、後半セクションまたは折りたたみ（`<details>`）へ分離します。
  - **基本構文（Level A Syntax）の採用**: 最初の実行例は、標準的な `import`、変数代入、単純な関数・メソッド呼び出しだけで構成し、1つのコードブロックに詰め込む新規概念を最小限に抑えます。

### 1.3 視覚的連続性と「偽の床（False Floor）」の回避
- **なぜそうするのか（Why）**:
  冒頭のタイトルやバッジの直後に、孤立した水平線（`---`）や大きな余白、画面を埋め尽くす巨大バナーが配置されると、読者の脳は「ここでページのコンテンツが区切られた（終わった）」と錯覚します（イリュージョン・オブ・コンプリートネス／偽の床）。その結果、下部に有益な手順が書かれていてもスクロールされにくくなります。
- **具体的な操作（How）**:
  - 最初の画面の末尾に次の見出しや導入コードの一部が覗くような視覚的連続性を保ちます。
  - 見出し（`##` / `###`）自体が持つ余白とタイポグラフィで十分にセクションが区切られる箇所では、装飾目的の水平線（`---`）の乱用を控えます。

## 2. 第2の柱：認知負荷と構造（Cognition & Structure）

### 2.1 作業記憶の保護（チャンキングと構造化）
- **なぜそうするのか（Why）**:
  人間が作業記憶（ワーキングメモリ）の中で同時に保持・比較できる情報の塊（チャンク）は3〜5個前後です。1つの見出しの下に7個も10個も箇条書きや設定項目がフラットに並ぶと、読者の作業記憶が飽和し、後半の項目が読み飛ばされます。
- **具体的な操作（How）**:
  - 5個以上の項目がフラットに並ぶ箇所は、意味的な共通軸で3〜4個の上位カテゴリ（小見出しやネストされたグループ）に束ねます。
  - 複数の要素が同じ属性（名前・型・デフォルト値・説明など）を持つ場合は、長文の箇条書きではなく比較軸を揃えた表（テーブル）に構造化します。

### 2.2 注意の分散（Split-Attention）と冗長な反復の解消
- **なぜそうするのか（Why）**:
  「上部のコードブロックの15行目にある引数 `foo` は〜」のように、参照対象（コードや図）と解説テキストが空間的に離れていると、読者は視線を上下に往復させるだけで認知資源を消耗します（注意の分散効果）。逆に、コードを見れば一目瞭然の字面をそのまま自然言語で繰り返すだけの説明（「`timeout: 30` はタイムアウトを30に設定します」等）は、余計な処理負荷を増やすだけで実質的な理解を助けません（冗長性効果）。
- **具体的な操作（How）**:
  - **空間的近接**: 実行コマンドの直後に期待される出力例を添え、重要な引数の説明はコードブロックの直近またはインラインコメントとして配置します。
  - **非トートロジー解説**: コードや設定名の字面をなぞる説明を省き、コードの字面からは読み取れない「前提条件」「単位」「副作用」「省略時や異常時の挙動」を記述します。

### 2.3 情報を削らない段階的開示（グルーピング × 関心事の分離）
- **なぜそうするのか（Why）**:
  初見の読者は「まず全体像と動かし方を素早く知りたい」と考える一方、本番導入やトラブルシューティングを行う読者は「省略されていない完全な仕様・エッジケース」を求めます。要約によって詳細情報を削り落とすと深い検証ができなくなり、逆に最初から全フラグや内部例外をフラットに並べると全体像が見えなくなります（透明性の逆説）。
- **具体的な操作（How）**:
  - **情報を削除・圧縮しない**: 詳細な仕様や背景情報は削るのではなく、配置場所（レイヤー）を分離して保持します。
  - **3層の関心事分離（Separation of Concerns）**:
    - **第1層（最短動線）**: 概要、解決する課題（Why/When）、最小実行例。
    - **第2層（主要概念と境界）**: 基本的な使い方、主要な設計選択の理由、運用上の制約と対処法。
    - **第3層（網羅的リファレンス）**: 全CLIフラグ・環境変数一覧、高度な設定、内部アーキテクチャ詳細、ベンチマーク生データ。
  - **媒体に応じた分離手法と目次**: Markdown環境では `<details>` 折りたたみまたは別ファイルへのリンク、プレーンテキスト環境では末尾の `Appendix（付録）` セクションへの分離を用います。実質的な主要見出し（H2、あるいは言語別セクション配下のH3等）が4個以上並ぶ場合は、文書の規模や好みに応じて冒頭・各セクション頭に目次（TOC）を置くか確認し、必要な場合に配置します。

### 2.4 説明的図解と装飾的視覚要素の区別
- **なぜそうするのか（Why）**:
  文字だけでは追いにくい構造や状態遷移を補う「説明的図解（アーキテクチャ図やフローチャート等）」は読者の理解を助けますが、本文と意味的結びつきが薄い装飾的グラフィックや定型記号（絵文字など）は、読者の視覚探索を位置や見出しによる素早い走査から「意味の照合」へ変えて探索速度を落とし、初見の読者や負荷の高い読者の注意を散らす場合があります。また、テキスト内に直接埋め込まれた絵文字はスクリーンリーダーで Unicode 記述子（ALTテキスト）として毎回音声読み上げ・点字出力されるため、行頭での反復や意図と異なる記述子によって文脈の読解が遮られることがあります。
- **具体的な操作（How）**:
  - **図解の役割と空間統合**: 図やダイアグラムを用いる場合は、見出しや本文の理解を直接補う内容を選び、解説テキストと空間的に近接させます。
  - **記号への依存回避と配置の配慮**: 装飾的な絵文字や視覚記号を用いる場合も、重要な意味の伝達を記号だけに委ねず周囲のテキストで読めるようにし、同じ記号を見出しや箇条書きの先頭へ連続配置する代わりに本文・項目の末尾へ寄せるなどの調整を検討します。
  - **表示環境への配慮**: CLI ツールの `--help` 出力やプレーンテキスト環境のように文字のみで完結する媒体では、端末やフォントによって絵文字が崩れたり表示幅が乱れたりする点に留意し、素の文字とインデントによる構造化を選びやすくします。

## 3. 第3の柱：論理と必然性（Logic & Necessity）

### 3.1 既知から未知への接続と論理の正規化（迂回の排除）
- **なぜそうするのか（Why）**:
  文章の理解は「読者がすでに知っている前提（旧情報・Topic）」を足場にして「新しい結論（新情報・Stress）」を受け取ることで進みます。前提で定義していない専門用語や内部モジュール名が手順の途中に唐突に出現したり、その場限りの抽象的な造語を導入して直後で言い換えるだけの回りくどい前置き（論理の迂回）があったりすると、読者の推論が途中で停止します。
- **具体的な操作（How）**:
  - **旧情報から新情報への連鎖**: 「Aという課題がある → その原因はBにある → Bを解決するためにCという仕組みを採る」のように、前の文の結論を次の文の前提としてつなぎます。
  - **時系列・条件関係の明示**: 処理の順序や並行・排他関係（「Aの完了後にBが走る」「Aの実行中にBが割り込む」等）を曖昧な接続詞（「そして」「また」）で済ませず、時間的・論理的な前後関係が定まる表現で記述します。
  - **迂回の削除**: 後続の文脈で使われない一時的な造語や抽象的な前置きを省き、前提から結論へ最短のステップでつなぎます。

### 3.2 背理法（境界条件）・対偶とトレードオフ（結果論証）の峻別
- **なぜそうするのか（Why）**:
  設計の必然性を説明する際、既存手法との「一長一短のトレードオフ（速度とメモリのバランス等）」であるにもかかわらず、「既存手法では破綻する／不可能である」と論理的不可能性のように書くことは論理的な飛躍であり、その既存手法を熟知している読者からの信頼を損ないます。また、「条件 A を満たせば特性 B を得る」という主張だけを書いて裏側の条件（対偶）を確認せずにいると、読者に適用範囲を過度に広げて誤解させる余地が残ります。
- **具体的な操作（How）**:
  - **背理法（論理的不可能性・境界条件）**: 「要件X（例：ブラウザのオフライン環境のみで完結すること）を満たす必要がある。方式Aは外部API通信を前提とするため、要件Xと両立しない」のように、前提要件との構造的な矛盾が成立する場合にのみ、不可能性の論証を用います。
  - **対偶による適用範囲の限定**: 「条件 A を満たせば特性 B を得る」と主張する際は、その対偶にあたる「特性 B が不要な（あるいは成り立たない）状況であれば条件 A を採る理由はない」という裏側の境界をあわせて確認し、不要な場面にまで対象や推奨を広げないように記述を整えます。
  - **結果論証（トレードオフ比較）**: 複数の方式がいずれも成立する場合は、「方式Aはメモリ消費が小さい反面、初回解析に時間を要する。本ツールは起動速度を優先するため方式Bを採用している」のように、条件付きのトレードオフとして記述します。

### 3.3 規範的説教（ought）から仕様事実・条件付き因果（is / If-Then）への転換
- **なぜそうするのか（Why）**:
  「XはYという性質を持つ（事実：is）」という命題から、「したがって読者はZすべきである／Zしなければならない（当為：ought）」という命令や義務を直接導き出すことは論理的に成立しません（ヒュームのギロチン）。また、書き手からの一方的な「〜すべき」という説教調の文体は、読者の自律的な判断権を脅かし、心理的な反発（リアクタンス）を引き起こします。
- **具体的な操作（How）**:
  - 文中の「〜すべきである」「〜しなければならない」「〜する必要がある」という規範表現を、**「仕様上の事実・制約（is）」** または **「目的・条件と結果の因果関係（If-Then）」** に書き換えます。
  - **変換の型**:
    - NG（規範・説教）: `本番環境では必ず --strict フラグを有効にすべきです。`
    - OK（条件付き因果・仕様事実）: `--strict フラグを指定すると、未定義の環境変数が検出された時点でプロセスが終了コード 1 で停止します。設定漏れによる意図しないデフォルト動作を防ぎたい本番環境などの運用に適しています。`

## 4. 第4の柱：誠実さと信頼（Credibility & Persuasion）

### 4.1 無根拠な誇張・安易な視覚的装飾の排除と比較基準（Baseline）の明示
- **なぜそうするのか（Why）**:
  生成AIやテンプレートによって美辞麗句（「超高速」「圧倒的」「革命的」「究極の」「爆速」等）や装飾的な視覚要素（内容と無関係な絵文字の連打など）を並べるコストがゼロになった現在、比較対象・測定条件を伴わない形容詞や過度な装飾は「中身のない宣伝（チープトーク）」として読者の警戒を招き、書き手の専門性や信頼感の評価を下げる要因になります。また、非言語記号（絵文字・記号類）単体での表現はOSやフォント環境による描画差や解釈のズレを生みやすく、読み上げ支援環境では意図しないノイズになることがあります。
- **具体的な操作（How）**:
  - **実測データがある場合**: 「何と比較して（Baseline）」「どの環境・条件で（OS / CPU / データ件数 / 計測方法）」「どの程度の差が出たか」を明記し、環境や入力サイズによって結果が変動する旨を添えます。
  - **実測データがない場合**: 主観的な形容詞（「高速な」「軽量な」「直感的な」）を削除し、「どのアルゴリズム・仕組みを使っているか」「外部依存ライブラリが何個か」「何ステップの操作で実行できるか」といった、読者が客観的に検証できる機能的事実へ置き換えます。
  - **記号・視覚的装飾への依存を避ける**: 重要度・ステータス・注意喚起などを記号や絵文字のみに委ねず、明示的な言語表現で言い切ります。技術文書や公式説明など冷静な信頼性が求められる文脈では、著者の明確な表現意図（Seed）でない限り装飾的な絵文字や感嘆的演出を抑え、絵文字を完全排除したい場合は [references/emoji-control.md](emoji-control.md) の任意オプション手順へ進みます。

### 4.2 反論あり両面提示（Refutational Two-Sided Disclosure）
- **なぜそうするのか（Why）**:
  長所だけを並べた文書は誇大広告として疑われやすい一方、正直に書こうとして「〇〇には非対応です」「〇〇はできません」と弱点だけを裸で箇条書き（反論なし両面提示）にすると、読者に「採用を見送る理由」だけを渡す結果になり、かえって説得力が低下します。
- **具体的な操作（How）**:
  - ツールの価値の根幹を否定しない中程度の制約・非推奨ケースを全体の1〜2割程度の分量で開示したうえで、以下の3要素をセット（反論あり構造）で記述します：
    1. **制限・非推奨の事実**: 何が対象外・制限事項であるか（例：100MBを超える単一バイナリファイルの解析には向かない）。
    2. **設計上のトレードオフ理由**: なぜあえてその制限を受け入れているのか（例：ストリーム分割を行わずメモリ上で一括AST変換を行うことで、通常サイズのファイルでの実装の単純さと応答速度を優先しているため）。
    3. **対処法・代替案**: その制限に該当する場合にどう回避するか、またはどの別ツールが適しているか（例：`--max-size` でスキップするか、巨大ログのストリーム処理にはツールXを利用する）。
  - ※表現の形式は文書のトーンに合わせ、仕様書のように項目ラベル付きで構造化しても、固定ラベルを使わずに自然な1段落の文章としてつなげて記述しても構いません。

### 4.3 追試可能な検証手段とコードとの整合性
- **なぜそうするのか（Why）**:
  ドキュメントに書かれたフラグ名、設定キー、ファイルパスが実際のソースコードと1箇所でも食い違っていると、読者は手元でエラーに直面し、文書全体の記述を信用しなくなります。また、主張や仕様を読者自身が手元で確かめる手段が用意されていると、文書への信頼が確立されます。
- **具体的な操作（How）**:
  - ドキュメント内のコマンド、引数、設定ファイル名、ディレクトリ構成が現在のリポジトリの実装（`package.json`, `Cargo.toml`, `pyproject.toml`, CLIパーサー定義等）と一致しているかを必ず照合します。
  - 実用ツールやライブラリでは、テストスイートの実行コマンドや動作確認コマンドを明記し、読者が手元で動作を追試できるようにします。
