## 1. 第4の柱：論理と必然性（Logic & Necessity）

### 1.1 既知から未知への必然性の連鎖と時系列・条件関係の明示
- **なぜそうするのか（Why）**:
  文章の理解は、読者がすでに共有できる前提（旧情報）を足場にして新しい結論（新情報）を受け取ることで進みます。単なる機能スペックの列挙や「〜が高速になります」という結果の断定だけでは、なぜその結果が成り立つのか納得できません。また、曖昧な接続詞（「そして」「また」）で処理をつなぐと、順序・並行・排他の関係が読者に誤解されます。
- **具体的な操作（How）**:
  - **旧情報から新情報への連鎖**: 「現場でAという具体的な不便がある → その原因はBにある → Bを解消するためCという仕組みを採る」のように、前の結論を次の前提としてつなぎます。
  - **機能 → 動作機序 → 変化の結合**: 機能を説明する際は、「どの仕組み（機能）が → どのように作用し（動作機序） → 読者の作業や結果がどう変わるのか（変化）」の因果鎖が切れていないかを確認します。
  - **時系列・条件関係の明示**: 処理の前後関係や排他条件（「Aの完了後にBが走る」「Xが失敗した場合はYへフォールバックする」等）を、関係が一意に定まる表現で記述します。

### 1.2 論理の正規化（迂回除去・未定義語彙の点検）と構造的一致
- **なぜそうするのか（Why）**:
  後続で使われない一時的な造語や抽象的な概念をわざわざ導入して直後で言い換えるだけの前置き（論理の迂回）は、読者の推論を遠回りさせます。また、前提で定義していない内部識別子・略語・独自用語が本文や手順の途中に唐突に出現すると理解が止まります。さらに、ドキュメントの見出し構造が実際のソフトウェアのモジュール構造とズレていると、保守と理解の負担が増えます。
- **具体的な操作（How）**:
  - **迂回の削除**: 後続の文脈で使われない一時的な造語や回りくどい前置きを削り、前提から結論へ直接つなぎます。
  - **未定義語彙の点検**: 手順や解説の途中に前段で未定義の内部キー名・略語・設定識別子が唐突に出ていないか確認し、読者が知っている表現へ置き換えるか、必要な場合のみ初出で文脈を補います。
  - **構造的一致の確認**: アーキテクチャ設計書や仕様書では、見出し階層が実際のディレクトリ・モジュール構造やデータフローと対応しているかを確認します。

### 1.3 背理法（境界条件）・対偶とトレードオフ（結果論証）の峻別
- **なぜそうするのか（Why）**:
  ソフトウェア設計の多くは「速度とメモリのバランス」のような因果的トレードオフ（結果論証）です。それにもかかわらず、他方式のトレードオフを「従来手法では破綻する・不可能である」と論理的不可能性（背理法）のように誇張すると、既存手法を知る読者からの信頼を損ないます。また、「条件 A なら特性 B を得る」の裏側（対偶）を確認しないと、適用範囲を過度に広げて誤用を招きます。
- **具体的な操作（How）**:
  - **背理法（論理的不可能性）**: 「要件X（例：外部通信なしの完全オフライン動作）が必須である。方式Aは外部API通信を前提とするため、要件Xと構造的に両立しない」のように、必須要件との明確な矛盾がある場合にのみ用います。
  - **トレードオフ（結果論証）**: 複数方式がいずれも成立する場合は、「方式Aはメモリ消費が小さい反面、初回解析に時間を要する。本ツールは起動速度を優先し方式Bを採用している」と条件付きで書き分けます。
  - **対偶による境界確認**: 「条件 A なら特性 B を得る」と書く際は、「特性 B が不要な状況であれば条件 A を採る理由はない」という裏側の境界を確認し、不要な場面へ推奨を広げないようにします。

### 1.4 規範的説教（ought / should）から仕様事実・条件付き因果（is / If-Then）への転換
- **なぜそうするのか（Why）**:
  「XはYという仕様である（事実：is）」という命題から、「したがって読者はZすべきである／Zしなければならない（当為：ought）」を論理的媒介なしに導くことはできません。また、書き手からの「〜すべき」という説教調は読者の自律性を脅かし反発を招くうえ、API仕様における `should` / `should not` といった曖昧な規範表現は「破ると何が起きるのか」をぼかし、利用者に不要な防御コードや疑問を増やします。
- **具体的な操作（How）**:
  - 文中の「〜すべき」「〜しなければならない」「〜する必要がある」「`should` / `should not`」を点検し、**「仕様上の事実・制約（is）」** と **「目的・条件と結果の因果関係（If-Then）」** へ書き換えます。
  - 例: `本番では必ず --strict を有効にすべきです` → `--strict を指定すると、未定義の環境変数を検出した時点で終了コード 1 で停止します。設定漏れによる意図しない既定値動作を防ぎたい本番運用に適しています。`

## 2. 第5の柱（前半）：信頼と誠実さ（Credibility & Honesty）

### 2.1 無根拠な誇張・フォーマット装飾バイアスの排除と比較基準の明示
- **なぜそうするのか（Why）**:
  生成AIによって美辞麗句（「超高速」「圧倒的」「革命的」「究極の」「爆速」等）や過剰なフォーマット装飾（無目的な太字乱用、定型絵文字の連打、無意味な区切り線）を出力するコストがゼロになった現在、比較基準や測定条件のない自称と装飾は「中身のない宣伝」として読者の警戒を招きます。また、非言語記号（絵文字等）はOS・フォント差による描画ズレや解釈のばらつきがあり、テキスト文脈を添えても完全には解消しません。
- **具体的な操作（How）**:
  - **実測データがある場合**: 「何と比較して（Baseline）」「どの環境・条件で（OS / CPU / データ件数 / 計測方法）」「どの程度の差が出たか」と、環境・入力サイズによって変動する旨の但し書きを添えます。
  - **実測データがない場合**: 比較基準のない主観的形容詞（「高速な」「軽量な」「直感的な」「細かな」等）を見直し、「どのアルゴリズム・方式を使うか」「外部依存が何個か」「何ステップで実行できるか」といった検証可能な機能的事実へ置き換えます。
  - **装飾バイアスと記号依存の回避**: 重要度・警告・境界条件を絵文字や太字の演出だけに委ねず明確な言葉で記述し、太字や箇条書きが理解の補助ではなく見栄えの飾りになっていないかを点検します。

### 2.2 反論あり両面提示と主張の論拠・成立範囲の明示
- **なぜそうするのか（Why）**:
  長所だけを並べる文書は誇張を疑われやすい一方、「〇〇には非対応です」「〇〇はできません」と弱点だけを裸で箇条書きにすると、読者に不採用の理由だけを渡してしまい、かえって説得力が低下します。制限事項に「なぜその設計を選んだか（トレードオフ理由）」と「どう対処・代替できるか」を添えることで初めて、書き手の誠実さへの信頼と導入判断のしやすさが両立します。
- **具体的な操作（How）**:
  - ツールの価値の根幹を否定しない中程度の制約・非推奨ケースを隠さず挙げたうえで、次の3要素をセットで記述します（固定ラベルの有無は文書のトーンに合わせ、自然な段落として書いても構いません）。
    1. **制限・非推奨の事実**: 何が対象外か、どの規模・条件で限界に達するか。
    2. **設計上のトレードオフ理由**: 何を優先した結果としてその制限を受け入れているか。
    3. **対処法・代替案**: その条件に該当する場合の回避手段、または適した別ツール・方式。
  - 中心となる主張についても、「なぜそう言えるのか（データ・論拠・裏付け）」と「どの前提・規模の範囲で成り立つのか（成立範囲の限定）」が読者に伝わるか確認します。
