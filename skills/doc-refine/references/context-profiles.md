## 1. なぜ文脈適応と読者層の見極めが必要なのか

どれほど優れた設計原則であっても、すべての文書に同じ見出し構成・同じ情報密度・同じ形式を機械的に当てはめると逆効果になります。
- **読者層の熟練度による反転**: 専門外の初見読者には専門用語を抑えた導入と最小実行例が役立ちますが、すでにドメイン知識を共有している同僚や保守担当者向けの内部仕様書に初歩的な導入を書くと、かえって読解の邪魔になります（専門性の逆転）。逆に、保守引き継ぎ文書で細粒度の境界条件や内部構造を省くと実用になりません。
- **手慣れた形式と目的のトレードオフ**: 操作手順書のようにシナリオが明確な文書は手順の一貫性が重視される一方、概念や設計思想を伝える文書では前提から結論への論理と図解が鍵になります。また、読者や書き手は慣れ親しんだ「箇条書きだらけの形式」を主観的に好む傾向があるため、文見出しや表へ切り替える際は対象文書の目的と読者層に照らして自然なバランスを選びます。
- **書き手の「種（Seed）」と自律性の保護**: ジョークアプリや個人制作物に重厚な課題論証や3段構えの免責リストを押し付けると本来の魅力が消えて野暮になります。また、マークアップが使えないプレーンテキスト（`.txt`）に GitHub 専用記法を持ち込むと崩れます。

そのため、Stage 2 で「誰が何のために読むのか」「書き手が伝えたい核（種）は何か」を見極めたうえで、5つの柱の重み付けと適用範囲を調整します。

## 2. 文書種別・プロジェクト性質ごとの重み付けガイド

### 2.1 実用CLIツール・OSSライブラリ・SDK
- **読者の関心**: 「自分の課題を解決できるか」「今すぐ手元で動かせるか」「本番や自分の環境に入れて安全か（境界や罠はないか）」。
- **重点を置く原則**:
  - **初動と最短動線**: 最初の画面での具体的入出力定義・Why / When、単一の標準インストール手順と基本構文による最小実行例。
  - **空間構造と形式選択**: ハッピーパス（第1層）と詳細リファレンス（第3層）の段階的開示、オプション・フラグ一覧の表構造化（並列構文で走査速度を上げる）。
  - **境界開示と検証可能性**: 比較基準付きデータ、反論あり両面提示（制約事実＋理由＋回避策）、具体的な値域制約と動的I/O具体例、手元で追試できるテストコマンド。
- **あえて控える要素**: 説明文中の頻繁な問いかけ、意味的距離の遠い装飾記号の乱用。

### 2.2 エンタメ・ジョークアプリ・個人Webトイ
- **読者の関心**: 「何これ面白い」「どうやって遊ぶの」「なぜこれを作ったの」。
- **重点を置く原則**:
  - **入口の動機づけと「種」の保護**: ユーモアや温度感を保ったまま一目で何のおもちゃか伝わる冒頭文、デモ画面（スクリーンショットやGIF）、公開URLや制作背景記事への分かりやすい導線。
  - **手軽な体験手順と軽快な呼吸**: ブラウザで開くだけ、あるいは数コマンドで試せる手順と、テンポよく読める文体。
- **あえて控える要素（野暮の回避）**:
  - 堅苦しい学術的・工学的な課題定義の長文。
  - 大袈裟なパフォーマンス比較表や重々しい3段構成の免責・制約セクション（動作環境や軽い注意書きで足りるなら自然な1〜2文に留める）。
  - 短い文書に無理やり `<details>` 折りたたみ・目次・過剰な値域仕様表を入れてクリックの手間を増やすこと。

### 2.3 内部アーキテクチャ設計書・仕様書・RFC
- **読者の関心**: 「なぜ代替案ではなくこの設計を選んだのか」「モジュール間の境界とデータフローはどうなっているか」「エッジケースや異常時にどう振る舞うか」。
- **重点を置く原則**:
  - **論理と構造的一致**: 前提課題からの演繹的連鎖、背理法（必須要件との矛盾）とトレードオフ比較の峻別、実際のディレクトリ・モジュール構造と対応した見出し構成、説明的ダイアグラム。
  - **厳密な境界と契約**: `should` や `invalid` を避けた検証可能な仕様事実・条件付き因果、値域制約・状態遷移表・動的I/O具体例（境界値・エラー系含む）。
  - **散文の呼吸とスメル除去**: 絡み合い（Tangled）や断片化（Fragmented）を避け、設計判断の散文では構文の単調さを防ぐ。
- **あえて控える要素**: パッケージ公開用バッジや、対象に存在しない「1行インストール（Quick Start）」の押し付け。

### 2.4 技術解説記事・Zenn / note / ブログ・論考
- **読者の関心**: 「どんな問いやきっかけから始まったのか」「どういう仕組み・理屈なのか」「自分の開発や思考にどう活かせるか」。
- **重点を置く原則**:
  - **共感を生む入口（種）と文見出し**: 書き手の素直な疑問や動機から入り、見出しと目次で全体の見通しを作る。論点を伝える節では主張の分かる文見出しと図解を活用する。
  - **時間的リズムと既知から未知への語り口**: 一呼吸で追いやすい係り受け・句読点、長文と短文の緩急、構文のゆらぎ。節の切り替えに要点直結の問いかけを1つ置くのは有効だが、本文中で高頻度に乱発しない。
  - **非説教トーン**: 「〜すべき」で読者にマウントを取らず、事実・条件付き因果・知見共有のスタンスを保つ。

### 2.5 プレーンテキスト（`.txt`）・コード内コメント・PR説明
- **読者の関心**: マークアップのない環境やコードレビュー中に、素早く要点・変更理由・境界条件を把握すること。
- **重点を置く原則**:
  - **記法非依存の段階的開示とチャンク化**: `<details>` が使えない環境では冒頭に結論・要約と主要手順を置き、詳細は末尾の `=== Appendix ===` または別ファイルへ分離する。空行とインデントで3〜5項目の塊を作る。
  - **非トートロジーと動的例**: コードコメントでは字面の言い換えを避け、背景（Why）・不変条件・境界挙動を書く。PR説明では変更前後の具体的な入出力・再現確認コマンドを添える。

### 2.6 操作主体が人間以外の対象（Agent Skill・AIプラグイン・自動化ボット等）
- **読者の関心**: 「自分の環境へどう導入するか」「人間側はどう頼めば（または何をトリガーに）動くのか」「どこで自動進行が止まり、どこで人間の判断が必要か」。
- **重点を置く原則**:
  - **人間側インターフェースの優先提示**: 最初の画面と主要動線（第1層〜第2層）には、導入手順、自然言語での依頼例やトリガー条件、人間が確認・承認するポイントを配置する。
  - **内部実装と人間向け情報の層分離**: エージェントやボットが裏側で実行する補助スクリプトの引数仕様・手動実行・CI連携などの詳細は第3層（折りたたみ、または `docs/` 等の人間向け外部リファレンス）へ分離し、エージェント自身が読み込むスキル内リファレンス領域とは混ぜない。
- **あえて控える要素**: 人間が普段直接叩かない内部スクリプトのコマンドやフラグ一覧を、あたかも人間向けの主たる使い方であるかのように冒頭や中盤へ並べること。

### 2.7 一般のテキスト文書（業務手順書・企画書・ガイド・一般解説等）
- **読者の関心**: 「この文書は何を決め、何ができるようになるのか」「自分の状況や業務に当てはまるか」「次に何を確認・判断・実行すればよいか」。
- **重点を置く原則**:
  - **初動の結論と適用範囲（Why / When）**: 冒頭で文書の目的・対象読者・成立条件を具体的な言葉で示し、3〜5チャンクの束ねと目次・段階的開示で見通しを作る。
  - **呼吸の通る文体と誠実な条件提示**: 一呼吸で追える文構造と形式の使い分け（箇条書き・文見出し・表・図解）、規範的な押し付け（「〜すべき」）を排した事実と条件付き因果（If-Then）、例外や制約の理由・代替策を揃えた両面提示。
- **あえて控える要素**: 対象に存在しないソフトウェア用の導入コマンド・コードスニペット・API値域表の無理な当てはめや、読者層の領域外となる専門用語の持ち込み。
