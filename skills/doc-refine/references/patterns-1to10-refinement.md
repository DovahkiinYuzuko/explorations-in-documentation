# 1→10 リライトパターンカタログ (patterns-1to10-refinement.md)

本ドキュメントは、既存のドキュメント（README、仕様書等）を精査・推敲・リライトする際に、作業者（AI）が適用すべき置換ルールおよび浄化パターン集である。

---

## 1. 「何と比べてやねん！」撲滅フィルタ（未定義形容詞の事実化）

根拠のない大言壮語や、比較対象が明示されていない抽象的な形容詞（BAKAワード）を検出し、客観的な数値・ベースライン・測定環境付きの事実命題へ置換する。

### 対象となる表現パターン
- 「圧倒的に高速」「超軽量」「最高峰」「究極の柔軟性」「極めてセキュア」
- 「業界標準を凌駕するパフォーマンス」「極限まで無駄を削ぎ落とした設計」

### 置換規約
1. **比較対象（Baseline）の明記**: 何と比べて、どの条件下で、どのような測定結果が得られたのかを記述する。
2. **環境注記アラート（`[!NOTE]`）の付与**: 実測値やベンチマークを提示する場合、必ず測定環境（ハードウェア、ランタイム、データセット）を開示する。
3. **無機質な機能的事実への変換**: 測定データが存在しない場合は、形容詞を削除し、「何を入力して何を出力するのか」という機能的挙動のみを淡々と記述する。

#### 置換例
- **Before**: `本ライブラリは、超高速で軽量な JSON パーサーです。`
- **After**:
  ```markdown
  本ライブラリは、C++20 の `std::string_view` を用いたゼロコピー設計の JSON パーサーです。
  
  > [!NOTE]
  > 開発環境（AMD Ryzen 9 7950X, Ubuntu 24.04, GCC 13.2）における 10MB の JSON 走査テストにおいて、標準ライブラリ比で処理時間 42ms（約 2.1 倍）を記録しています。実測値は実行環境やデータ構造により変動します。
  ```

## 2. ヒュームのギロチン・フィルタ（規範文の客観事実化）

「〜すべきである（ought）」「〜しなければならない」「〜する必要がある」といった説教・規範論を検出し、読者の自律性を尊重した「条件付き因果・機能的事実（is）」へ変換する。

### 背景とエビデンス
- **David Hume (1739)**: 事実命題（is）から当為命題（ought）は論理的に導出できない。
- **Nabwire et al. (2026)** / **Cemiloglu & Ali (2021)**: システム利用において、強迫的な説教や規範の押し付けは心理的リアクタンス（反発）を引き起こし、継続利用意図を損なう。客観的な透明性の提供が信頼の 57.8% を説明する。

### 置換ルール
| 検出パターン | 置換後の構文 | 具体例 (Before $\rightarrow$ After) |
| :--- | :--- | :--- |
| 「開発者は〜すべきです」 | 「〜を意図する場合、〜を設定します」 | `接続プールは必ず10以上に設定すべきです。` $\rightarrow$ `高頻度アクセス時の接続枯渇を防ぐ場合、接続プールサイズを 10 以上に設定します。` |
| 「〜しなければなりません」 | 「〜という仕様・制約があります」 | `本関数を呼ぶ前に必ず init() を実行しなければなりません。` $\rightarrow$ `内部バッファの初期化仕様上、本関数は init() の実行完了後に呼び出せます。` |
| 「〜するのが推奨されます」 | 「〜のトレードオフがあります」 | `本番環境では Docker を使うことが強く推奨されます。` $\rightarrow$ `本番環境において環境差異を完全に隔離する場合は、Docker コンテナ構成を利用できます。` |

## 3. 認知負荷低減の構造化

読者の作業記憶（Working Memory）のオーバーフローを防ぎ、情報を跳躍探索できる視覚的・構造的配置に再編する。

### パターン 3.1: チャンキング（$4 \pm 1$ の原則）
- **Cowan (2001)** / **Miller (1956)**: 人間の純粋な作業記憶容量の中央値は **4** である。
- **規約**: 単一の見出し直下に並列するリスト項目、機能紹介、引数一覧は最大 4〜5 個に抑える。それ以上になる場合は、意味的なサブカテゴリ（2〜3個の見出し）に分割する。

### パターン 3.2: 構造的目次（TOC）の配備
- **Su et al. (2012, IEEE/IFIP)** の情報採餌理論（Information Foraging）:
- **規約**: H2 見出しが **4個以上** 存在するドキュメントでは、冒頭（ファーストビュー直後）に構造的目次（Markdown TOC）を必ず配置する。

### パターン 3.3: 注意分割効果（Split-Attention Effect）の解消
- **Sweller et al. (2011)** / **Kalyuga (2011)**: コード例とその解説文が空間的に離れていると、視線往復によって外在性認知負荷（ECL）が急増する。
- **規約**:
  - コードスニペットの直下に、そのスニペット専用の解説（引数の意味や出力結果）を密結合して配置する。
  - 「上のコードの3行目は〜」のような遠隔参照を避け、インラインコメントまたは直下の箇条書きで一体化させる。

## 4. 制約の3要素化（反論なき欠点列挙の是正）

単に箇条書きで「〇〇は非対応です」「△△はできません」とだけ書かれた記述を是正する。

### 背景とエビデンス
- **Allen (1991)** / **O'Keefe (1999)**: 弱点を単に列挙しただけのドキュメント（Non-refutational）は、読者の不安を煽り、説得力・信頼性を低下させる（$r = -.060$）。
- 必ず「理由」と「回避策」を併記して反論あり両面提示（Refutational）に転換する。

### リライト手順
1. **制約の特定**: 何が制限されているのか（メモリ上限、非対応OS、スレッドセーフティ等）。
2. **アーキテクチャ理由の付与**: なぜその制約が存在するのか（安全性優先、シンプルさ維持、外部依存削減等）。
3. **ワークアラウンドの提示**: 読者はどのような代替手段・設定をとるべきか。

#### 置換例
- **Before**:
  - Windows では動作しません。
  - 1GB 以上のファイルは扱えません。
- **After**:
  - **Windows 環境非対応**:
    - **事実**: 本ツールは POSIX 準拠のシグナル制御に依存しているため、Windows ネイティブ環境では動作しません。
    - **理由**: プラットフォーム固有の抽象化レイヤーを排し、バイナリサイズとレイテンシを極小化するためです。
    - **回避策**: Windows 環境では WSL2（Windows Subsystem for Linux）経由で実行してください。
  - **1GB 以上の巨大ファイル処理**:
    - **事実**: 1GB を超えるファイルを単一走査する場合、Out of Memory が発生する可能性があります。
    - **理由**: 高速なオンメモリ差分検出を優先したインデックス構造を採用しているためです。
    - **回避策**: 1GB 以上の巨大データを扱う場合は、`--chunk-size 256M` オプションを指定して分割ストリーミング処理を有効にしてください。

## 5. コスト高シグナル（Costly Signal）への転換

スター数やダウンロード数といった安価なシグナル（Cheap Talk）に依存せず、読者が手元で検証できる再現コマンドを配備する。

### 背景とエビデンス
- **Paramitha et al. (2026)** / **Asa & Nautwima (2026)**: ソーシャルプルーフ（スター数等）はAI生成や操作により信頼性を喪失している。模倣コストの高い客観的シグナル（手元でのテスト実行性、再現コマンド）のみが読者の信頼を獲得する（$t = 3.27, p < .005$）。

### 規約
- ドキュメント末尾または検証セクションに、読者が手元でツールの正常動作やテストスイートを1行で再現実行できるコマンドを明記する。
```bash
# テストスイートの実行（動作検証）
npm test
# または
pytest tests/ -v
```
