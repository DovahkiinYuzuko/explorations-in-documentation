# 0→1 新規起案パターンカタログ (patterns-0to1-creation.md)

本ドキュメントは、新規プロジェクトやドキュメント（README等）をゼロから設計・起案する際に、作業者（AI）が適用すべき工学的パターン集である。

---

## 1. 必然性の因果鎖 (Chain of Necessity)

ドキュメントの冒頭において、「なぜこのツールが存在するのか（Why）」の因果関係を読者と共有する。

### 背景とエビデンス
- **Prana et al. (2019)** の393リポジトリ解析によると、READMEにおける「How（使い方）」の含有率は 88.5%、「What（機能）」は 97.0% に達する一方、「Why（存在理由・設計動機）」の含有率はわずか **25.7%（欠落率 74.3%）** である。
- Why が欠落している場合、読者は「自分のユースケースに適合しているか」を判断できず、離脱率が急増する。

### 3段因果チェーンの構文
1. **根源的前提（Axiom）**: 誰もが直面する具体的な不便・課題・前提条件（客観的事実）。
2. **解決機能（Mechanism）**: その課題を解消するために実装した機能。
3. **設計必然性（Architecture）**: なぜその構造・仕様を選択したのかという工学的理由。

#### 記述例
```markdown
## 背景と設計思想
分散環境においてログの順序性が崩れると、障害原因の特定に平均数時間のトレース作業を要します。
本ツールは、分散ノード間のタイムスタンプ揺らぎを吸収するため、物理時刻ではなく論理クロック（Lamport Timestamps）に基づく順序付けを採用しています。
これにより、中央集権的な同期サーバーを必要とせず、ローカル環境のみで完全な因果順序を復元します。
```

## 2. ファーストビュー規約 (Above the Fold)

読者がページを開いた直後（最初の画面スクロール前、概ね冒頭50行以内）に、ツールの本質を確定させる。

### 背景とエビデンス
- **Nielsen Norman Group (2018)** のアイトラッキング研究によると、全閲覧時間の **57% はファーストビュー（Above the Fold）** に集中し、上半分に 65% 以上が集中する。
- **Julian Shapiro (2020)** の Adoption Rate 理論: $\text{Adoption Rate} = \text{Utility} - (\text{Labor} + \text{Confusion})$。最初の数秒で以下の3問に即答できなければ読者は離脱する。
  1. What is it?（これは何か）
  2. Why does it matter?（なぜ自分にとって重要か）
  3. How do I get started?（どうやって動かすのか）

### パターン 2.1: LSP One-Liner 構文
**Hellman et al. (2023)** の調査において、読者に最も好まれる説明文形式は LSP パターン（Language, Software technology, Purpose）である。
```
[対象言語 / 動作環境] 向けの [ソフトウェア種別] であり、[解決する具体的課題 / 提供機能] を実現します。
```
- **OK例**: `Python 3.10+ 向けの静的型解析拡張 CLI であり、SQL クエリ文字列の構文エラーを実行前に検出します。`
- **NG例**: `超高速で究極の使いやすさを誇る、革新的なデータベースツールです。`（形容詞のみで言語・種別・機能が不明）

### パターン 2.2: 騙しの床（False Floor）の排除
- **Shanelle Mullin / CXL (2023)**: ファーストビュー直下に巨大な水平線や余白を配置すると、読者は「ここでコンテンツが終了した」と誤認してスクロールを停止する。
- 冒頭には不要な空行や無意味な区切り線を置かず、直後に「Quick Start」の見出しが覗く配置にする。

## 3. Level A Quick Start (最小実行可能コード: MWE)

ファーストビューの直後に、初学者が迷わず動かせる最短の手順を提示する。

### 背景とエビデンス
- **Sitthithanasakul et al. (2023)** の PyPI 1,620 ライブラリ解析によると、ドキュメントのコード例の **92% は基本構文（Level A: 代入、属性参照、import のみ）** で構成されている。
- 内包表記、ラムダ式、非同期処理などの高度構文（Level C: わずか 1%）を Quick Start で使うと、初心者の認知的負荷が急増し導入を妨げる。

### 規約
1. **3行以内の実行完結**: インストールから最小の実行結果が得られるまでを最短行数で示す。
2. **自己完結性**: 外部APIキーの事前取得や複雑な設定ファイルなしで、コピペして即座に動く最小例（MWE: Minimum Working Example）にする。

#### 記述例
```bash
# インストール
pip install fast-query

# 実行（最小例）
fast-query check schema.sql
```

## 4. 反論あり両面提示 (Refutational Two-Sided Disclosure)

強みだけでなく、ツールの制約・限界・非推奨ケースを客観的に開示する。

### 背景とエビデンス
- **O'Keefe (1999)**（$k = 107$ のメタ分析）および **Allen (1991)**（$N = 7547$）の実証:
  - **反論なし両面提示（単に弱点を列挙しただけ）**: 説得力が有意に低下する（$r = -.060, p < .05$、逆効果）。
  - **反論あり両面提示（弱点＋設計理由＋回避策）**: 片面提示（良いことだけ書く）を有意に上回る信頼性と説得力を獲得する（$r = .077, p < .001$）。
- **Rubin & Benbasat (2023, ACM TMIS)**: トゥールミンモデルに基づく Rebuttal（例外・制約条件）の自己開示は、読者の「誠実さ（Integrity）への信頼」を有意に高める（$t = 1.99, p < 0.05$）。

### 3要素タプル構文
制約事項を記述する際は、必ず以下の3要素を1セットとして記述する。
1. **制約事実 (Constraint Fact)**: 何ができないのか、どこで性能限界に達するのか。
2. **設計理由 / トレードオフ (Design Rationale)**: なぜその仕様を選んだのか（アーキテクチャ上の必然性）。
3. **回避策 / 推奨運用 (Alternative / Workaround)**: 読者はどう対処すればよいのか。

#### 記述例
```markdown
## 制約事項と境界条件
- **10万件以上のリアルタイム結合処理**:
  - **事実**: 単一テーブルのレコード数が10万件を超える場合、インメモリ結合ではメモリ消費量が急増します。
  - **理由**: 分散合流アルゴリズムではなく、単一プロセスの高速走査を優先した軽量設計を採用しているためです。
  - **回避策**: 10万件を超える大規模バッチ処理では、`--stream` フラグを有効にするか、事前集計テーブルをご利用ください。
```

## 5. 3層情報分離アーキテクチャ (Progressive Disclosure)

すべての情報を1ページに平坦に並べず、深度（Depth）を保ったまま階層化する。

### 背景とエビデンス
- **Anik & Bunt (2026, IUI '26)**: ユーザーは省略された要約よりも詳細な技術情報（High Information Depth）を強く好む。段階的開示（Progressive Disclosure）は、高深度な情報を提示する際に生じる認知負荷を有意に緩和する（$p < 0.05$）。
- **Springer & Whittaker (2020, ACM TiiS)**: 初期画面で細かな不確実性や低水準エラーを過剰に露出させると、ユーザーはシステム全体への不信感を募らせる。

### 3層の構成
| 階層 | 対象読者 | 配置場所 | 含まれるコンテンツ |
| :--- | :--- | :--- | :--- |
| **Tier 1: 概要・最短動線** | 全読者 | 本文冒頭（ファーストビュー） | LSP One-Liner、最小Quick Start、主要バッジ |
| **Tier 2: 体系解説・機能** | 導入検討者 | 本文中部 | 主要機能とユースケース、制約事項（3要素構文）、アーキテクチャ概要 |
| **Tier 3: 詳細仕様・内部構造** | 実装者・上級者 | `<details>` 折りたたみ、または別ファイル（SoC） | 全CLIフラグ一覧、詳細設定スキーマ、ベンチマーク測定環境詳細、FAQ |
