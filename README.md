「嘘や誇張がなく、頭に入りやすい『良いドキュメント』とは何か」を探求した自由研究（[**`PAPER.md`**](./PAPER.md)）と、その設計原則を実装したエージェントスキル `doc-refine` のリポジトリです。形式論理学、認知科学、広告工学、言語心理学の先行研究を横断し、テキストベースの情報設計論（仮説モデル）としてまとめています。

生成AI（LLM）がドキュメントを書く際には、根拠のない誇張表現が混ざったり機械的な事実確認が省かれたりする課題があります。本リポジトリでは、単なる「てにをは」の校正や画一的な穴埋めテンプレートではなく、READMEをはじめ、仕様書・設計解説・解説記事・手順書・プレーンテキストのメモといったドキュメント全般に応用できる情報設計のレンズを提案しています。

## 仮説モデルの全体像

本編 **[`PAPER.md`](./PAPER.md)** では、読者が文書を開いてから理解し行動に移すまでの処理プロセスに沿って、仮説モデルを3部・5本柱で構成しています。

### Part I：知覚・構造・リズムの設計（読みやすさの基盤）
1. **視線と初動の科学（第2章）**:
   読者の注意は最初の画面（Above the Fold）に集中しやすく、多くのOSSでは「なぜ作ったか（Why）」「いつ使うか（When）」が欠落しがちです。これを踏まえ、冒頭での字義通りの定義、単一の最短導入手順、偽の床（False Floor）や視覚探索遅延の回避を扱います。
2. **空間構造と認知負荷（第3章）**:
   初見情報に対するワーキングメモリの制約と、「読者は要約ではなく深い情報を求める」という知見を両立させるには、情報を削らない設計が求められます。「グルーピング × 関心事の分離（SoC）」による3層への段階的開示に加え、箇条書き・文見出し＋図解・表・グラフの使い分け、さらに説明的図解と装飾的視覚要素（絵文字など）が理解度やスクリーンリーダーに与える影響を整理します。
3. **文章のリズムと呼吸（第4章）**:
   黙読時の内語を支える音韻ループの時間制約（一呼吸）に着目し、係り受けの複雑さや機械的な短文化による語彙密度過多を避けるバランスを探ります。一覧での並列構文と散文での構文ゆらぎの使い分け、APIドキュメントに現れる5種のスタイル欠陥、および説明文における問いかけ（挿入質問）の有効範囲を扱います。

### Part II：論理と誠実さの設計（納得と信頼の基盤）
4. **論理と必然性の骨格（第5章）**:
   前提となる不便から機能・動作機序・変化への必然性の鎖をつなぎ、背理法（論理的不可能性）とトレードオフ（結果論証）を書き分けます。ヒュームのギロチンに照らして「〜すべき」という規範的説教を控え、客観的な仕様事実と条件付き因果文で語る姿勢を重視します。
5. **信頼・誠実さと境界開示（第6章）**:
   根拠のない美辞麗句やAI由来のフォーマット装飾バイアスに頼らず、比較ベースラインと測定環境、手元で追試できる再現コマンド、そして「制約事実・トレードオフ理由・回避策」を揃えた反論あり両面提示を用います。あわせて、曖昧な制約表記を避けた具体的な値域境界・動的入出力（I/O）具体例の提示と、読者の熟練度による分かりやすさ評価の乖離を扱います。

### Part III：文脈適応とモデルの限界
6. **「テンプレート」ではなく「思考のレンズ」として（第7章）**:
   固定の穴埋めフォームや一律の禁止ルールを押し付けると、文書の目的や書き手の個性が損なわれます。実用CLIツール、ライブラリ、Agent Skill 等のドキュメント、内部設計書、一般の手順書や解説記事、エンタメ系Webトイ、プレーンテキストといった対象と読者層に応じて、各原則の重み付けを柔軟に変える運用を想定しています。

## エージェントスキル `doc-refine` の導入と使い方

### 導入コマンド

標準的な導入方法（Skills CLI 対応環境）は次のコマンドです。

```bash
npx skills add DovahkiinYuzuko/explorations-in-documentation --skill doc-refine
```

Antigravity 環境ではプラグインとして導入できます。

```bash
agy plugin install https://github.com/DovahkiinYuzuko/explorations-in-documentation
```

導入後は、対応するエージェントのチャットから対象ファイルを指定して呼び出すか（例：「`README.md` を `doc-refine` で見直して」「この設計書のドラフトを `doc-refine` で整えて」）、スラッシュコマンド対応であれば

```bash
/doc-refine
```

で呼び出せます。

### 実行の仕組み（4-Stage Pipeline）

`doc-refine` は文書の規模と変更範囲に応じて **Full**（新規作成・全面改稿）と **Lite**（1セクション追記・短いメモ等）の2モードを切り替え、次の4段階で文書を組み立てます。

1. **Stage 1（事実収集）**: 実装コード・設定・テストからコマンド、パス、値域、境界挙動などのファクトリストを抽出します。
2. **Stage 2（裸の最小構成ブループリント＋合意）**: 形容や装飾を削ぎ落とした論理骨格と配置案を提示し、書き手の動機や不足情報を確認して合意を取ります。
3. **Stage 3（自然言語化と形式実装）**: 確定した骨格とファクトを削らずに配置し、構造化形式と黙読のリズムを整えて執筆します。
4. **Stage 4（次元別の独立監査・ステージング確認・反映）**: 執筆直後の確証バイアスを避けるため、Part I（知覚・空間構造・リズム）と Part II（論理・誠実さ・境界・実装整合）の2系統に分けて監査し、競合を調整したうえでステージング用の物理ファイルへ書き出し、承認を経てから本番の実ファイルへ反映します。

## 制約事項とトレードオフ

本研究の仮説モデルおよびスキルの境界条件とトレードオフを開示します。

- **異分野統合モデルとしての未検証性と対象領域ギャップ**:
  各先行研究には個別の実験・調査の裏付けがありますが、それらを統合した本モデル自体について大規模な被験者実験による直接的な実証は現時点で行われていません。引用文献には学習教材・メール・語学読解など非技術文書を対象とした研究も含まれます。個人の自由研究として、まずは散在する知見から演繹的に仮説モデルを組み立てスキルとして試作することを優先した結果です。確定した法則ではなく、実践と観測を通じて調整する思考のレンズとして参照する運用を想定しています。
- **情緒的記事・純粋なセールスコピーへの非適合と慣れのトレードオフ**:
  本フレームワークは、小説、ポエム、情緒的エッセイ、または感情的な高揚感で購買を促す消費者向けセールスレターには向いていません。技術文書であっても、装飾を抑えた構成や文見出しへの切り替えは、従来の箇条書きスタイルに慣れた読者から主観的な物足りなさを持たれる場合があります。認知負荷の軽減・論理の明快さ・アクセシビリティの維持を優先した設計であり、感情的共感や第一印象の華やかさを主目的とする文書では従来のレトリックや物語論の技法が適しています。
- **初期執筆・維持・検証コストの増加**:
  比較ベースラインの確認、値域境界や動的I/O具体例の整理、実装変更への追従には、短い宣伝文句を書く場合と比べて書き手側に相応の手間がかかります。書き手が手間を省いた結果として読み手側に探索労力や誤用トラブルが生じる構造を反転させ、書き手側でそのコストを引き受ける選択を意図しています。人間がゼロからすべてを担う負担を減らすため、核となる動機や判断を人間が持ち、事実照合や構造整理を `doc-refine` で補助する併用を想定しています。
- **非圧縮原則に伴う単一ファイルサイズの増大と折りたたみ表現の環境依存**:
  情報を要約・省略せずに値域境界、動的I/O具体例、トレードオフ理由まで1つのファイル（`README.md` 等）にすべて盛り込むと、`<details>` で視覚的に折りたたんでいてもファイル自体のバイト数・行数は元の規模より膨らみやすくなります。<br>これは読み手が外部サイトやソースコードを再探索する手間を減らすためにまず情報の網羅性を優先しているためですが、もし書き出された文書を実際に読んでみて「1ファイルとしては長すぎる」「サイズが大きすぎる」と感じた場合は、どこまでを1枚に残し、どこからを別ファイル（`docs/` 等）へ切り出すか（関心事の分離）を検討するひとつの目安になり得ます。また、`<details>` による開閉表現自体もMarkdown・HTMLレンダラ環境に依存するため、プレーンテキスト（`.txt`）やRFC等の非マークアップ環境でも同様に、末尾付録（Appendix）や外部ファイルへの分離として適用できます。
